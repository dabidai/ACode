# ACode 阶段六：MCP 工具生态 — spec

> 最后更新：2026-08-26
> 对应 MCP（Model Context Protocol）规范 2025-06-18 版（stdio / Streamable HTTP 两种传输）

## 背景

ACode 目前的工具集是封闭的：六个内置工具（读文件、写文件、编辑、glob、grep、bash）加两个会话工具（AskUser、ExitPlanMode），由代码硬编码注册。要接入 GitHub Issue 查询、数据库操作、Slack 消息这类外部能力，只能改代码、加内置工具——每次都要改主程序再发版。

MCP（Model Context Protocol）是 AI 工具接入的开放标准：社区已经写好大量 MCP Server（GitHub、数据库、Slack、Notion……），每个 Server 通过协议暴露一组工具。本阶段让 ACode 成为 MCP 客户端：用户在配置文件里声明一个 MCP Server，ACode 启动时自动接入它提供的工具，注册进工具中心，Agent 调用时无感——从封闭工具集变成开放工具生态，不改一行代码。

## 目标用户

- 本人：复用社区 MCP Server，把 ACode 的 Agent 能力延伸到 GitHub/数据库/Slack 等外部系统
- 后续阶段潜在使用者：终端开发者、习惯命令行工作流的用户，在配置里声明即接入

## 能力清单

1. JSON-RPC 2.0 协议层：请求、响应、通知三种消息的编解码，单入口按消息形态判别类型（含错误响应与数字/字符串 id 归一）
2. 传输抽象 + 两种实现：stdio（启动子进程、管道全双工通信、换行分隔 JSON 帧）与 Streamable HTTP（远程 Server、请求-响应 + 响应体按内容类型分流 JSON / SSE）
3. MCP Client：初始化握手（协议版本协商容错）→ 初始化完成通知 → 工具列表发现（含分页）→ 工具调用，全程请求-响应按消息 id 异步匹配、超时兜底
4. 工具适配器：把远端工具包装成 ACode 内部 Tool 接口——工具名加 server 名前缀、参数 schema 原样透传、描述标注来源，Agent 与权限体系无感
5. 连接管理：多个 server 的连接缓存与生命周期——stdio 进程常驻、HTTP 会话保持；启动时逐个连接、单个失败不阻断应用；退出时清理子进程；工具调用遇连接死亡自动重连一次
6. 配置声明：配置文件的 mcp_servers 段声明 server 列表，支持命令启动型（可带参数与显式环境变量）与 URL 型（可带请求头），公共超时与权限档，可用开关禁用单个 server
7. 环境变量隔离：子进程只拿到最小必需的环境变量集合（平台相关）加配置显式声明的变量，不泄露 API 密钥等敏感信息
8. 权限对接：server 级权限档声明，未声明时按最严档处理（调用前确认、规划模式不可见），已声明只读的 server 在规划模式可见
9. Windows 原生支持：`.cmd`/`.bat` 启动器自动经 shell 包装，npx/uvx 类命令直接可用

## 非功能要求

- **零新增依赖**：协议编解码复用现有 JSON 库，HTTP 传输用 JDK 内置客户端，不引入第三方 MCP SDK / HTTP / SSE 库
- **启动容错**：任一 server 连接失败（进程启动失败 / 握手超时 / 网络不通）→ 跳过该 server 的工具并输出警告，ACode 正常启动，其余 server 不受影响
- **失败不终止循环**：远端工具执行失败返回带错误标记的工具结果，模型看到错误后可换策略继续，Agent Loop 不中断
- **超时兜底**：握手与工具调用统一受超时上限约束，超时返回失败结果而不是永久挂起
- **进程洁净**：退出时销毁 stdio 子进程，不留残留进程；子进程意外死亡被及时感知并触发重连
- **并发安全**：协议层按消息 id 异步分发响应，响应乱序可达，多请求并发安全
- **隔离最小化**：子进程环境严格白名单化，未声明的本机环境变量一律不透传
- **可测试**：协议/传输/客户端各层独立可测，用假 server 进程与本地 HTTP server 做端到端验证，不依赖真实 MCP Server 或网络

## 设计骨架

### 分层结构

```
┌────────────────────────────────────────────────────┐
│  配置层：config.yaml 新增 mcp_servers 段             │
│  → 解析成 server 配置列表（命令启动型 / URL 型）        │
├────────────────────────────────────────────────────┤
│  连接管理层：MCP Manager                            │
│  （逐个连接全部 server · 失败跳过 · 注册工具 · 退出清理）│
├────────────────────────────────────────────────────┤
│  连接单元：server 连接（连接缓存 + 懒重连）           │
├────────────────────────────────────────────────────┤
│  协议层：MCP Client（握手/工具发现/工具调用/按 id 匹配）│
│  JSON-RPC 编解码 ◄── Transport 抽象 ──► 远端 Server   │
│       ┌──────────────┴──────────────┐                │
│  StdioTransport             HttpTransport           │
│  （子进程管道）              （JDK HTTP 客户端）      │
├────────────────────────────────────────────────────┤
│  工具层：Tool 接口适配器（server 名前缀 + schema 透传）│
│  → ToolRegistry → Agent / 执行器 / 权限体系（现有链路）│
└────────────────────────────────────────────────────┘
```

### 一次工具调用的完整路径

```
用户声明 mcp_servers（命令启动型 / URL 型）
  → 启动：逐个连接 → 握手（协议版本协商）→ 工具发现（含分页）→ 注册进工具中心
  → 运行时：Agent 决定调用远端工具
      → 权限检查（按 server 权限档，默认最严档）
      → 工具适配器调用连接单元 → 协议层发 JSON-RPC 请求（带消息 id）
      → Transport 送往远端（stdio 写子进程 / HTTP POST）
      → 按 id 匹配响应 → 适配器转成工具结果回填模型
  → 退出：销毁子进程、释放连接
```

### 关键设计决策（已确认）

| 决策点 | 结论 |
|---|---|
| SSE 边界 | Streamable HTTP 的响应体按内容类型分流：纯 JSON 直接解析；`text/event-stream` 用事件解析（只取消息事件）。不做独立 SSE 长连接传输 |
| 失败策略 | 单个 server 连接失败 → 跳过该 server 工具、输出警告、应用照常启动 |
| 工具命名 | 远端工具注册名 = `server名_工具名`，从根上规避与内置工具、多 server 之间的重名冲突 |
| 权限档 | server 配置可声明权限档（read/write/exec）；未声明默认 exec（最严档：调用前确认、规划模式不可见）；声明 read 的 server 规划模式可见 |
| 重连 | 工具调用时发现连接死亡 → 自动重连一次；重连失败返回工具错误，不无限重试 |
| 握手版本 | 客户端声明新版协议版本；server 返回旧版本时告警但不中断（本实现只用两版本间兼容的方法子集） |
| 环境隔离 | 子进程环境 = 平台最小必需集 + 配置显式声明，其余一律不传 |

## Out of Scope（本阶段明确不做）

- 独立 SSE 长连接传输（2024-11-05 版「HTTP+SSE」传输形态）
- MCP 的 Resources / Prompts 消费（读资源、模板提示词）
- MCP 的 Sampling / Elicitation 等客户端侧高级能力（向模型采样、模态获取）
- 服务端主动发起的请求（收到时统一回「不支持」错误，不实现具体处理）
- 工具列表动态变更推送（tools/listChanged）
- server 级认证框架（OAuth 等：仅支持配置静态请求头透传）
- 非 Windows 平台的 shell 包装细节与 Unix 特有环境差异的逐项打磨（白名单保留基本项，以平台判别的通用集合为准）
