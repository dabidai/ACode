# ACode 阶段十四：Agent Teams —— 从一次性子任务到长期协作团队 — spec

> 最后更新：2026-09-13
> 功能诉求见 `prompt.md`（本章对应**教材站点第 15 章**，章节号差 1；教材站点第 13 章 = ACode `ch12`，第 14 章 = ACode `ch13`）；本文只定"做什么/为什么"，不含函数名、参数名、默认值与错误文本；具体阈值、工具 schema 与全部文案集中在 `checklist.md` 顶部
> 已确认的前置决策：本章**只做 in-process 后端**（tmux/iTerm2 pane 后端留作后续增量）；队员中间过程**不做终端流式渲染**，只提交结果行（规避多路并发渲染冲突）；团队状态**会话内落盘、重启不恢复**（队员 transcript 持久化除外）；共享任务列表**不设队员/任务数量硬上限**（规模治理留给 LLM）；ch12 遗留的五项基础设施**接手两项、留三项**（见「跨章接口」）

## 背景

前两章解决了「别互相踩」：ch12 让主 Agent 能把活派给上下文隔离的子 Agent，ch13 给每个 Agent 配独立的工作目录。但两者的共同形状是「派出去 → 等结果 → 拿回来」，一条直线：

- **一次只能等一个活**：主 Agent 派一个子 Agent 后阻塞等待，结构上没有「同时盯几个活」的位子。A、B 互不依赖、C 依赖 A、D 依赖 B 的活，被迫串行改完。
- **子 Agent 之间没有通道**：发现线索只能绕主 Agent 中转，主 Agent 沦为信息交换机。
- **主 Agent 派完队员后自己还留着全套工具**：一边协调一边自己改代码，和队员的修改直接冲突，调度信息与自己干活的信息在同一个上下文里互相干扰。

本章让主 Agent 从「派临时工」升级到「带一个团队」：队员能并行、能互相说话、能自己认领活。与业界框架（AutoGen / CrewAI / LangGraph）的差别是：**ACode 没有调度器**——协调能力以工具的形式发给每个队员（共享任务列表 + 异步邮箱），由 LLM 自己看着办。代价是拿不到确定的执行图，收益是新增协作方式只需加工具、不动调度器。这是本章的骨架。

## 目标用户

- **本人（日常使用者）**：把「涉及多个模块、可并行推进」的任务交给一个团队去做，主 Agent 只负责拆活、派人和收口，不再事事亲为。
- **主 Agent（内部消费者）**：获得一组新的顶层工具（建团队、任务管理、队员通信），以及一个可选的协调模式身份。
- **后续阶段**：pane 后端等增量建立在本章完整团队能力之上。

## 能力清单

### 一、团队结构与生命周期

1. **团队结构**：一个团队 = 组名 + 负责人 + 花名册。负责人就是主 Agent 自己（Lead 是主 Agent 多出来的一个身份，不是新 Agent）；花名册记录每个队员的名称、Agent 实例、类型、模型覆盖、Worktree 路径、后端类型、活跃状态、是否需要 Lead 审批。
2. **队员的存在性即状态**：活跃状态只有「活跃 / 空闲」两值，没有「已终止」——队员终止后直接从花名册移除，不留墓碑。
3. **建团队是独立顶层工具**：创建团队是一个有明确边界的操作（改变 Lead 的运行模式），不作为派子 Agent 的副作用发生。创建时完成四件事：检测执行后端、写团队配置、初始化共享任务列表、把 Lead 注册进团队。
4. **重名自动避让**：同名团队已存在时自动在名字后追加序号，而不是报错打断用户。
5. **拆团队 = 安全清理**：所有队员空闲且各自 Worktree 满足安全删除条件时清理；仍活跃或有未保存成果时拒绝，返回原因。
6. **派队员走既有 Agent 工具**：Agent 工具增加「指定团队」参数——参数非空时，被派出的子 Agent 以队员身份加入该团队；往团队里加人的权力只属于 Lead。
7. **清理守卫**：任务完成、队员空闲并核实成果已保留后清理 Worktree 与团队目录；不满足条件就保留现场并说明原因。

### 二、共享任务列表与四个任务工具

8. **共享任务列表是协调底座之一**：团队级任务存储，队员可创建、查看、列举、更新。队员**自己从列表里认领**任务——系统不强制分配，让队员基于自己手头的上下文做选择。
9. **结构化依赖**：更新任务时可声明「阻塞了谁」与「被谁阻塞」两种互补写法的依赖字段，建立有向依赖图；队员看任务列表就能知道哪些被阻塞、哪些可以认领。**依赖未满足的任务不能被认领**（系统级约束，不是提示词劝说）。
10. **文本约定是补充**：核心依赖用结构化字段建立系统级约束，补充说明写在任务描述里（系统不解析自然语言依赖）。
11. **任务状态**：三值状态机（待认领 / 进行中 / 已完成）；「被阻塞」不是存储态而是派生态——依赖未完成时列表里标记为阻塞、认领被拒。**队员终止或崩溃时，其持有的进行中任务自动回滚为待认领**，可被其他队员重新认领（prompt 未明说这一点，是本章的补白，见「关键设计决策」）。
12. **认领的原子性**：同一任务只能被一个队员认领，并发认领恰一人成功——这是任务列表的并发正确性底线。

### 三、SendMessage 与文件邮箱

13. **队员间直接通信**：队员可以向指定队友发消息（按名字或 Agent ID 寻址，两者等价），也可以广播给全体队友。目标队员已停止时，系统自动把它从磁盘恢复起来继续工作（与「空闲与续写」联动）。
14. **纯文本消息必须带摘要**：摘要作为消息预览显示，让 Lead 和队友扫一眼消息列表就能知道每条说了什么，不需要逐条展开。摘要长度有硬性词数校验。
15. **结构化消息**：退出请求、退出回复、审批回复三类**生命周期与权限审批**事件做成协议化消息类型，不靠自然语言猜。其中审批回复只有 Lead 能发，退出回复只能发给 Lead。
16. **文件邮箱 + 轮询**：通信不是网络级实时直连。消息写进收件箱文件，收件人在自己下一轮循环开头读出，注入为系统提醒——异步但可寻址。同一套机制三种后端通用。
17. **名称注册表**：名字到 Agent ID 的映射表，发送时先解析名字；广播不查注册表。收件人不存在时报错，不静默丢弃。
18. **收件箱并发安全**：每个收件箱配独立锁文件，用原子创建抢锁、随机抖动重试和整文件原子替换避免并发写冲突；超龄锁仅在确认持有者已退出后回收。

### 四、队员运行时与续写

19. **in-process 队员**：每个队员是同一个进程内的独立 Agent 实例，跑在虚拟线程上，与 Lead 并行执行。生命周期绑在 Lead 身上——Lead 退出，队员一起消失（prompt 已接受的代价）。
20. **队员工具集 = 干活工具 + 协调工具**：基础工具与协调五件套按任务授权组成允许集合；`Agent`、团队管理和交互类工具对队员不可见，实际执行入口也核验同一集合。队员不能借完整注册表绕过模型可见范围。
21. **系统提示只加一段三行附录**：只解决一个问题——告诉队员「纯文本回复对队友不可见，想通信必须用消息工具」。工具列表本身自描述，工作流程由 Lead 通过任务与提示词传达，不硬编码在系统提示里。
22. **队员自己跑**：队员就是普通的 Agent 实例，在自己的循环里自主决定做什么。协调工具和读写工具一样只是工具列表里的选项，Agent 循环对它们不做特殊处理；「什么时候查消息、认领任务、给队友通气」由 LLM 判断。
23. **队员停止时两步通知 Lead**：队员认为活干完了（不再调用工具），系统标记其空闲，并向 Lead 的邮箱发一条空闲通知。Lead 据此判断该追加任务还是启动收敛。
24. **队员上下文持久化到磁盘**：队员空闲后、甚至被强制终止后，都可以通过发消息把它从磁盘上的对话记录恢复起来，带着完整历史继续工作。这是队员与普通子 Agent 的分界线——队员是持续性的工作者，不是一次性人力。
25. **任务完成通知**：队员执行结束（完成 / 失败 / 被杀）时，系统以结构化通知（含最终文本、token 用量、工具次数、耗时）投递给 Lead，Lead 据此续写或收口。

### 五、队员派生管线

26. **派队员六步**：加载 Agent 定义（指定了模型就覆盖）→ 分配 Worktree → 注入协调工具 → 按后端分流（本章只有 in-process）→ 注册名称 → 登记进花名册。
27. **定义式与 Fork 式**：指定 Agent 类型走定义式（空白上下文，适合职责明确的角色）；留空走 ch12 的 Fork 式（继承 Lead 对话历史）。
28. **队员必须获得独立 Worktree**：派生时分配经验证的独立工作目录；分配失败则派生失败并回滚注册，不把并行队员放进同一主目录。
29. **防扩张**：队员的「指定团队」参数被屏蔽——往团队里加人的权力只属于 Lead，防止团队规模指数级膨胀。

### 六、Coordinator Mode 与 Plan 审批协议

30. **Coordinator Mode 是独立于 Agent Team 的可选能力**：团队可以不开协调模式；进入后 Lead 只保留派人、通信、任务管理、团队管理和只读工具。可写文件或执行任意 shell 命令的入口均移除，并在执行端核验。
31. **两把锁**：一道开发者开关（配置）+ 一道用户开关（环境变量），两把都开才生效——避免在用户不知情的情况下改变 Lead 的行为模式。
32. **四阶段工作流提示词**：注入一套协调者系统提示，把大部分任务规范成「研究（队员并行）→ 综合（Lead 自己理解并撰写实施规格）→ 实施（队员）→ 验证（队员）」四阶段。**理解不能外包**：提示词明确要求 Lead 不能把「理解问题」的责任推回给队员——协调者的价值恰在于它是唯一能看到全局的人。
33. **Plan 审批协议**：花名册里的「需要审批」标记给高危队员加一道锁——审批前工具执行范围为只读，提交计划给 Lead 后等待结构化回复；批准后才获得本次明确批准的能力范围，拒绝或等待期间不得执行修改操作。审批的终端可视化留后续。

### 七、收敛与清理

34. **收敛由 Lead 判断**：所有任务完成后，Lead 在普通模式下依次合并各队员分支，能确认的冲突自行解决，无法确定的逻辑冲突报告用户；协调模式下不执行合并命令，须先退出该模式。
35. **不做内置合并工具**：合并冲突的解决本质上是语义理解，封装成工具会把它压成布尔返回值（ch13 已确立同款立场）。

## 非功能要求

- **零新增依赖**：文件邮箱、锁、JSON 存储全部用 JDK 与既有 Jackson；不引入消息队列、RPC 或调度框架。
- **逻辑层与终端解耦**：团队管理、任务存储、邮箱、名称解析都不依赖终端，可在无终端的单测里直接断言（沿用既有纯逻辑组件的风格）。
- **并发正确**：任务认领、邮箱写入、花名册注册在并发下必须正确（锁 + 原子操作）；并发测试可重复、不靠 sleep 赌时序。
- **队员故障不拖垮主循环**：队员异常、邮箱写失败、持久化失败都只记告警并通知，主循环继续；单个队员崩溃不影响其他队员与 Lead。
- **持久化失败不打断**：写盘失败只告警、不中断对话（沿用 session 包同款约定）。
- **能力边界优于行为约束**：队员的约束全部落在工具列表与参数屏蔽上，不靠提示词劝说。
- **测试隔离**：队员测试必须用 `@TempDir` 隔离，绝不读写用户真实的 `~/.acode/` 或真实仓库。

## 设计骨架

### 分层

```
┌────────────────────────────────────────────────────────────────────┐
│  Lead（主 Agent，团队负责人）                                       │
│  TeamCreate / TeamDelete / Agent(指定团队) / SendMessage            │
│  Coordinator Mode（可选）：白名单收窄 + 四阶段系统提示               │
├────────────────────────────────────────────────────────────────────┤
│  团队管理（生命周期 + 花名册 + 配置）                               │
│  创建/删除/清理守卫 · 队员注册/移除 · 活跃状态 · 重名避让           │
├──────────────────────┬─────────────────────────────────────────────┤
│  共享任务列表         │  文件邮箱 + 名称注册表                       │
│  状态机 + 依赖图      │  锁文件 + 重试 + 原子替换 · 名字→ID 解析     │
│  认领原子性 · 回滚    │  消息投递（指定 / 广播）· 轮询读回           │
├──────────────────────┴─────────────────────────────────────────────┤
│  协调工具（队员专属）：TaskCreate / TaskGet / TaskList /             │
│  TaskUpdate / SendMessage                                           │
├────────────────────────────────────────────────────────────────────┤
│  队员运行时（in-process）                                           │
│  虚拟线程 Agent 实例 · 干活工具 + 协调工具 · 每轮开头邮箱轮询        │
│  停止→标记空闲+通知 Lead · transcript 持久化 · 唤醒续写             │
├────────────────────────────────────────────────────────────────────┤
│  持久化（会话内工作状态，重启不恢复）                               │
│  .acode/teams/{团队}/：config.json · tasks.json · mailbox/ ·        │
│  transcripts/                                                       │
└────────────────────────────────────────────────────────────────────┘
```

### 队员的一次循环

```
每轮 Agent Loop 开头：从收件箱读出未读消息 → 注入为轮次级系统提醒
  → 请求模型（工具列表 = 干活工具 + 协调工具）
  → 有工具调用：执行（协调工具与普通工具一视同仁）
  → 无工具调用：结束 → 标记空闲 + 向 Lead 发空闲通知
Lead 侧：收到任务完成通知（完成/失败/被杀）→ 续写（发消息）或收口
```

### 团队生命周期

```
创建（建配置、检测后端、注册 Lead）
  → 分解（Lead 推理出任务与依赖，写入共享列表）
  → 派生（六步，队员各自跑）
  → 执行（队员自主认领、干活、通信）
  → 收敛（Lead 用 git 合并各 Worktree，冲突自行解决或上报用户）
  → 清理（全部空闲才允许拆台；删 Worktree、删团队目录）
```

## 关键设计决策

| 决策点 | 结论 |
|---|---|
| 后端范围 | **本章只实现 in-process 后端**（prompt 边界原文）。后端类型仍是队员级字段、机制与 pane 后端共享同一套任务列表与文件邮箱，但 tmux / iTerm2 两个取值留作后续增量。后端检测因此简化为恒 in-process，不做多分支检测与运行时回退。 |
| 队员中间过程的呈现 | **不做终端流式渲染**（本章范围收敛）。队员是后台任务，其流式文本、工具调用不直接画上屏；终端只提交三类结果行：任务完成通知块、空闲通知、消息摘要预览。理由：ACode 的渲染模型是「活跃区重绘 + 原生回滚」的单流结构，多路并发流式输出与它正面冲突，而 prompt 并未要求流式呈现队员过程——收敛为提交行既符合「后台任务」语义，也把这个风险从实现期直接消除。真机验收仍保留（多队员并行时终端输出必须不乱）。 |
| 邮箱轮询的注入点 | 复用轮次提醒通道，但消息读取与确认分开：请求成功进入模型调用后才确认投递；构建失败、取消或重试时未确认消息仍可重送。结构化审批回复需幂等处理。 |
| 认领的表达 | **认领 = 更新任务状态为「进行中」**，不新增认领工具。依赖未满足时认领被拒；「被阻塞」是派生态不是存储态。任务 ID 为团队内顺序递增的整数（与 prompt 示例一致）。 |
| 队员崩溃后的任务 | **其持有的进行中任务自动回滚为待认领**（prompt 未明说，本章补白）：队员终止/崩溃时花名册移除、不留墓碑，任务若不回滚将永远卡在「进行中」无人能认领，与「不留墓碑」的设计自洽。 |
| 团队持久化的语义 | **会话内落盘、重启不恢复**（prompt 边界原文的精确化）：团队配置、任务、邮箱、transcript 都落在团队目录下，作为**会话内的工作状态**——供队员共享、Lead 查看、续写恢复用；不提供「重启后恢复一个还活着的团队」的入口，进程退出后这些文件是残留物，由 TeamDelete 与清理步骤整目录删除。prompt 第一步「把团队配置持久化到磁盘」与边界「不做跨会话持久化」表面上冲突，本决策把两者统一为「会话内落盘」。 |
| 队员的工具集 | **干活工具 + 协调五件套，硬剔除四类**：Agent 工具、团队管理工具、向用户提问、退出规划（队员没有前台与规划状态，这些对队员无意义或有风险）。协调模式的白名单对 Lead 生效，与队员工具集是两套独立过滤。 |
| 队员系统提示 | **只加三行附录**（prompt 原文照抄，见 checklist 顶部），不把花名册与工作流程写进系统提示——工具自描述，工作流由 Lead 传达。 |
