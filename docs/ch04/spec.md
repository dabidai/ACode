# ACode 阶段三：Agent Loop — spec

> 最后更新：2026-08-14

## 背景

ACode 已完成对话层（阶段一）与工具调用（阶段二，ch03）。阶段二实现了「单步闭环」：模型发起工具调用 → ACode 执行 → 结果回传 → 再发一次请求出最终文本。但闭环被刻意收窄为两轮：第二次请求若模型仍要调用工具，ACode 只取文本并提示「连环调用未支持」。

从模型视角，它仍是「一步一停」的助手：每问一句最多干一步。本阶段加入 Agent Loop，让模型自主连续多步工作——读代码、写代码、跑命令、根据结果决定下一步，直到任务完成。ACode 从「能干活」升级为「能自主干活」。

## 目标用户

- 本人：在终端让 AI 自主完成多步编码任务，而非逐句指挥
- 后续阶段的潜在使用者：终端开发者、习惯命令行工作流的用户

## 能力清单

1. Agent 组件：持有模型客户端、工具注册中心、对话上下文与运行配置，驱动核心循环
2. ReAct 循环：一轮 = 请求模型 → 收集流式输出 → 有工具调用则执行 → 结果回填历史 → 下一轮；无工具调用则结束
3. 五种终止条件：模型自然收尾 / 达到轮数上限 / 用户取消 / 计划交付 / 流错误
4. 事件流：以事件队列对外暴露全过程，模型文本、工具调用、工具结果、轮次进度、结束原因、错误统一作为事件吐出，UI 按需消费
5. 流式收集器：实时透传文本增量给 UI，同时积攒本轮完整文本、工具调用与结束信号
6. 结束信号透传：两端协议解析流结束原因，区分自然结束与输出截断
7. 截断恢复：回复被输出上限截断时，把已生成内容入历史并注入继续提示让模型接着写，恢复次数有上限
8. 工具分批执行：读类工具并发执行、写类与命令类串行执行、结果按调用声明顺序回传
9. 可配置轮数上限：循环受最大轮数约束，触顶停止执行并提示，已完成结果保留在历史
10. Plan Mode：/plan 进入只读规划、/do 恢复执行；规划期只暴露读工具与计划交付工具
11. 计划落盘：交付的计划写入工作目录下的计划文件，供用户审阅与后续引用
12. UI 订阅渲染：文本流式、工具卡片、轮次进度、终止原因提示均由事件驱动渲染

## 非功能要求

- 循环可控：轮数上限可配置；循环任意时刻可被 Ctrl+C 中断，中断后状态一致、可继续对话
- 事件解耦：Agent 不感知 UI，UI 不感知循环，二者仅通过事件队列通信
- 并发安全：读类工具可并发，写类与命令类互斥串行，结果与调用声明顺序一致
- 历史完整：无论正常结束、取消还是触顶，每个工具调用都有对应结果回填历史，不产生悬空调用
- 上下文控制：沿用现有「超限丢弃最早消息」策略；超长工具结果进入历史前截断
- 可测试：循环、收集、分区执行、plan 编排等核心逻辑有单元测试，不依赖真实网络
- 持久化兼容：循环过程产生的仍是普通对话消息，会话保存/恢复无需特殊处理
- 计划可复用：交付的计划保存为文件，可在后续对话中引用

## 设计骨架

### 分层结构

```
┌───────────────────────────────────────────────┐
│  UI 层：文本流式渲染、工具卡片、进度与终止提示 │
├───────────────────────────────────────────────┤
│  事件订阅层：消费事件队列 → 驱动渲染与取消     │
├───────────────────────────────────────────────┤
│  Agent 层：循环编排（终止判定 / 截断恢复 /     │
│  plan 编排）+ 事件模型 + 流式收集器 + 分区执行器│
├───────────────────────────────────────────────┤
│  工具层：Tool 接口 / 注册中心 / 执行器         │
│  + 计划交付工具                                │
├───────────────────────────────────────────────┤
│  Provider 层：双后端流式协议 + 结束原因透传     │
├───────────────────────────────────────────────┤
│  消息模型层：content block 对话历史与持久化     │
└───────────────────────────────────────────────┘
```

- **Agent 层**是本章新增核心：持有循环状态，每轮「请求 → 收集 → 执行 → 回填」，全程对外发事件。
- **事件模型**是 Agent 与 UI 的唯一契约：UI 通过事件感知进度，通过取消信号反控循环。
- **Provider 层**只增加一件事：把协议层的流结束原因透传给上层，其余不动。
- **工具层**新增一个只读性质的计划交付工具，不感知循环。

### 关键设计决策（已确认）

| 决策点 | 结论 |
|---|---|
| 架构边界 | 抽独立 Agent 组件承载循环，对外以事件队列通信；UI 层订阅事件渲染 |
| 循环终止 | 五种情形：本轮无工具调用（自然收尾）/ 轮数上限 / 用户取消 / 计划交付 / 流错误 |
| 自然收尾信号 | 解析协议流结束原因：正常结束即代表模型主动收尾；与本轮无工具调用同时成立 |
| 截断恢复 | 流结束原因为输出截断时，已生成内容入历史 + 注入继续提示再循环，恢复次数有上限 |
| 错误处理 | 可重试错误发重试事件、按退避等待后再循环（有次数上限）；其余错误发错误事件终止 |
| 工具分批 | 读类并发、写类与命令类按声明顺序串行；所有读类先执行 |
| 结果对齐 | 执行顺序与回传顺序分离：执行可并发/串行，回传必须按模型声明顺序 |
| Plan Mode | /plan 进入、/do 退出；规划期只暴露读工具与计划交付工具；计划经交付工具落盘并结束循环 |
| 计划交付 | 模型以文本给出计划，交付时由 Agent 代为落盘为文件；规划期不需要写文件工具 |
| 权限 | 仅在工具执行前后保留拦截位，不实现具体规则（留给后续章节） |
| 上下文 | 沿用现有超限丢弃最早消息策略；不引入压缩/摘要 |
| 取消语义 | 取消信号贯穿流式收集与工具执行；未执行的工具调用以「已取消」结果补位，保证历史完整 |

### 循环数据流

```
用户输入
  → 逐轮循环（受轮数上限约束）：
     请求模型（携带历史 + 本轮工具集；plan 模式下附带规划提醒）
     → 流式收集：文本增量实时透传为事件；积攒本轮文本 / 工具调用 / 结束原因
     → 结束原因为截断：内容入历史 + 注入继续提示 → 继续下一轮
     → 流错误：可重试则发重试事件、等待后重试；否则发错误事件终止
     → 本轮无工具调用：正常结束
     → 有工具调用：
        分区执行（读类并发 / 写类与命令类串行，可被取消）
        → 结果回填历史（按声明顺序）
        → plan 模式下模型调用了计划交付工具：计划落盘 → 结束循环
        → 发轮次完成事件 → 继续下一轮
  → 达到轮数上限：停止执行、提示、保留已完成结果 → 结束
```

### 配置模型

沿用 YAML 两级配置。新增循环轮数上限字段（缺省即可用，具体默认值进 checklist）。不引入新的配置来源。

### 上下文与持久化

- 每轮请求组装时沿用现有超限丢弃策略，不新增压缩
- 截断恢复注入的提示消息、计划交付的调用与结果，都是普通对话消息，随会话保存/恢复
- 计划文件落盘在独立目录，不进入对话历史

## Out of Scope（本章明确不做）

- 复杂系统提示词组装（本章用最小可用提示词跑通循环）
- 完整权限策略：确认/拒绝流程、命令白名单、危险命令拦截（仅保留拦截位）
- 上下文压缩与摘要（长会话仍走丢弃最早消息）
- 交互式计划审批对话框（计划以普通文本展示）
- token 用量统计与展示
- 模型思考过程展示
- 子代理、MCP 接入
- 工具执行结果的折叠/回放交互
