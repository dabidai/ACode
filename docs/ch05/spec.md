# ACode 阶段五：工具权限确认（破坏性工具征求同意）— spec

> 最后更新：2026-08-16

## 背景

阶段二（ch03）工具层定义了 `Permission`（READ/WRITE/EXEC）元信息，但注释明言「仅标记、不拦截、不确认」：工具执行链路（`ToolExecutor`）对任何工具都不经用户同意直接执行。阶段三（ch04）Agent Loop 让模型自主连续调用工具，放大了这一风险——模型一发起 WriteFile / EditFile / Bash 调用，ACode 立刻落盘或执行命令。

修改文件、执行命令都属于有副作用、不可轻易回退的操作，理应执行前征求用户确认。参考 MewCode 书第三章工具设计：工具接口应暴露只读/破坏性元信息，权限系统据此决定是否放行（参考实现：`PermissionMode.decide` 返回 ALLOW/DENY/ASK、`PermissionResponse` 的 ALLOW/DENY）。

阶段五补上这道门槛：破坏性工具（写文件、执行命令）执行前弹 y/n 征求同意；只读工具（读文件、搜索）自动放行不打断。

## 目标用户

- 本人：不希望 AI 未经同意就覆盖文件或执行任意命令的终端用户
- 后续阶段潜在使用者：终端开发者、习惯命令行工作流的用户

## 能力清单

1. 权限门槛：非 READ 工具（WriteFile/EditFile/Bash）执行前弹出 y/n 确认
2. 只读放行：READ（ReadFile/Glob/Grep）工具自动执行，不弹确认、不影响既有并发调度
3. 确认信息：提示展示工具名与调用参数预览，用户据此判断是否放行
4. 拒绝语义：用户拒绝 → 返回「用户拒绝执行」的失败结果给模型，模型可调整方案后重试，不中断整轮
5. 取消等价拒绝：确认提示期间按 Ctrl+C（或 EOF）→ 按拒绝处理
6. 输入校验：非 y/n 输入重问，直到给出 y/n 或取消
7. 规划模式自然豁免：规划模式只暴露 READ 工具与计划交付工具，天然不触发确认
8. 事件握手：确认经事件队列双向通信——agent 线程发请求并阻塞等待，UI 主线程应答，无共享可变状态
9. 可测试：确认门槛可注入，默认放行，存量测试不受破坏

## 非功能要求

- 无死锁：确认期间 agent 线程阻塞但主线程持续消费事件队列并应答，握手必得答复
- 可观测：确认请求、批准、拒绝都以输出行可见，用户知道发生了什么
- 对只读工具零打扰：READ 路径不增加任何确认开销，并发调度行为不变
- 可测试：核心握手、拒绝语义、取消路径有单测，不依赖真实网络与真实终端
- 历史一致：被拒绝的调用也有失败结果入历史（is_error=true），无悬空 tool_use
- 注入友好：确认门槛与提示处理器均可注入，测试用桩驱动四路径

## 设计骨架

### 分层结构

```
┌───────────────────────────────────────────┐
│ UI 层：确认提示（弹 y/n、重问、取消）       │
├───────────────────────────────────────────┤
│ 事件订阅层：消费事件队列 → 渲染与应答       │
├───────────────────────────────────────────┤
│ Agent 层：循环编排 + 事件模型               │
│  + ConfirmationRequestEvent + Confirmation │
│  + ConfirmationGate（握手）                 │
├───────────────────────────────────────────┤
│ 执行器层：StreamingToolExecutor             │
│  执行非 READ 工具前先过确认门槛             │
├───────────────────────────────────────────┤
│ 工具层：Permission 元信息（READ/WRITE/EXEC）│
└───────────────────────────────────────────┘
```

### 关键设计决策（已确认）

| 决策点 | 结论 |
|---|---|
| 覆盖范围 | 非 READ 工具（WriteFile/EditFile/Bash）执行前确认；READ 自动放行 |
| 交互方式 | 终端弹 y/n 提示，逐调用确认，不做批量/会话级放行 |
| 拒绝行为 | 返回「用户拒绝执行」失败结果给模型，模型自调整；不中断整轮循环 |
| 通信机制 | 事件握手：agent 线程发 ConfirmationRequestEvent 阻塞等待，UI 主线程应答 |
| 取消语义 | 确认期间 Ctrl+C / EOF → 等价拒绝 |
| 注入性 | 确认门槛为可注入接口，默认放行；UI 提示处理器可注入桩 |
| 配置 | 本阶段不引入 allowlist 配置，保持纯交互式 |

### 确认数据流

```
执行器要对 WriteFile/EditFile/Bash 执行
  → 检查工具 Permission != READ
  → 构造 Confirmation，发 ConfirmationRequestEvent（含工具名/参数预览/答复通道）
  → agent 线程阻塞等待答复（await 期间可被取消）
  → UI 主线程收到事件 → 渲染「要执行 X … ？[y/n]」→ 读输入
       y → 批准；n → 拒绝；其他 → 重问；Ctrl+C/EOF → 拒绝
  → 答复回传 → agent 线程醒
      批准 → 正常执行该工具
      拒绝 → 返回 ToolResult.failure("用户拒绝执行「X」") → 照常发 ToolResultEvent → 结果入历史
```

## Out of Scope（本章明确不做）

- 配置文件 allowlist / 会话级「始终允许」/ 断点续传批量批准
- 命令危险检测：对 Bash 命令字符串做安全分析、危险命令白名单/黑名单
- 跨工具批量审批（本轮逐调用确认）
- 确认的持久化记忆（会话内不记忆用户偏好）
- 授权自动超时/回收
