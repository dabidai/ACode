## 论文要点（备忘）

- 问题：长上下文推理时 KV Cache 常驻 GPU，128K~512K 上下文显存不可承受。
- 方案：历史 KV 下沉 CPU Cold Pool，GPU 只留最近窗口 + 按需召回的关键 chunk；Neural Memory Indexer（独立 dual-encoder，只训 query 侧）根据当前 hidden state 预判未来会用到哪些历史 chunk；Sigmoid 阈值召回（非固定 top-k）；训练标签用 Cross-Layer Majority Voting 去噪。
- 效果：平均物理 KV Cache 压到 baseline 约 1/7（512K 时约 1/10）；平均准确率反升约 0.6pp（attention denoiser 效应）。
- 对照组落差：Recency Only 33.3、Random 10% 38.7 vs 检索感知 77.5 → "知道该召回哪些历史"才是关键。
- 局限：密集全局记忆任务（MRCR 76→48）失败；超出 512K 训练长度后选择质量退化接近随机；历史侧 key 冻结、与 backbone 解耦训练、无端到端联合优化。

## 对 ACode 的可能借鉴（仅假设，未定案）

ACode 是 API 客户端，服务端显存机制（LSA/Cold Pool/Memory Indexer 训练）不可迁移。若要借鉴，落在客户端概念层：

1. 现状超限裁最旧（Recency Only 语义）在长会话上会静默丢远距决策，且模型不知情；
2. "被裁历史可被按需取回"的冷池思想，与"裁剪前留一小段摘要保远距信号"两类方向；
3. "少塞噪声反升质量"提醒克制注入，避免自动记忆过度灌入上下文。

# 参考：agent-docs 第8章「上下文管理」理论学习摘记 — 设计笔记（ch8-1）

> 摘记对象：本地电子书 agent-docs（http://localhost/#/chapter-8-1，作者「派大星」）第8章「上下文管理，当Token开始烧钱」8-1 节「理论学习：上下文压缩与 Token 管理」。
> 定位：MewCode（参考 Claude Code）的**客户端**上下文管理方案。与上面 FlashMemory 那种 GPU 显存侧机制不同，它更贴近 ACode 可直接落地的形态，与 docs/ch07/prompt.md 的功能诉求逐条对应（对应关系见文末）。
> 记录时间：2026-09-03。原文配图 14 张位于 http://localhost/images/chapter-8-1/img-*.png，此处只保留文字要点，需要看图时再开站点。同章还有 8-2 实战 / 8-3 Go / 8-4 Java / 8-5 Python 源码解析，未纳入本节摘记。

## 动机与 Token 分布

- 无状态 API：每轮都要把完整对话历史发给模型，token 随轮次**线性增长**（第1轮 ~1K input，第20轮可到十几万）；撞上窗口上限 API 直接报错、Agent 瘫痪。
- 目标一句话：在有限 Token 预算内，保留最有价值的信息，丢掉可以牺牲的信息。
- Token 到底花在哪（工具结果是绝对大头，合计 ~85%）：

| 消息类型 | 典型 Token 量 | 占比 |
| --- | --- | --- |
| 固定开销（角色设定、环境信息、工具描述） | 5,000–15,000 | ~10% |
| 用户输入 | 50–500 | ~1% |
| AI 文字回复 | 200–2,000 | ~3% |
| 工具调用请求 | 50–200 | ~1% |
| 工具结果（文件内容） | 5,000–20,000 | ~55% |
| 工具结果（命令输出） | 500–5,000 | ~20% |
| 工具结果（搜索结果） | 500–3,000 | ~10% |

- 工具结果占比最高、又最容易过期（第3轮读的文件，第5轮改完后到第10轮旧内容仍占预算）→ 结论：**压缩先动工具结果，用户的对话反而要重点保留**。

## 两层压缩总览 + 设计哲学「能轻则轻」

| 层级 | 手段 | 信息损失 | API 开销 | 触发条件 |
| --- | --- | --- | --- | --- |
| 第 1 层 | 大结果存磁盘 | 几乎为零 | 零 | 工具结果超阈值 |
| 第 2 层 | 全量摘要（Auto-Compact） | 高 | 高（一次 API 调用） | token 数逼近窗口上限 |

- 哲学四个字：**能轻则轻**。轻量手段扛得住的，绝不动用昂贵的全量摘要。

## 第 1 层：大结果存磁盘（预防·近零损失·零成本）

- **单结果阈值**：> 50,000 字符（≈12.5K token）→ 完整结果写到本地文件，对话里只放一段预览（前 2KB）+ 文件路径；模型若要看全量可再 ReadFile 读回。零 API 开销、近零信息损失。
  - 对话中呈现形式：`<persisted-output>`"输出太大（80KB），完整内容已保存到 …；预览（前2KB）：…"（写入示例路径形如 `.mewcode/session/tool-results/toolu_abc123.txt`）。
- **每条消息聚合上限**：200K 字符。单条都没超（如并行 10 个 40K），合计超了照样处理——把最大的那些存盘替换，直到总量降到预算以内。
- **幂等写**：文件名用 `tool_use_id`（唯一、内容确定），以 `wx` 模式写入（文件已存在即跳过）。因为每次调 API 前都会重跑本层检查，写过一次就不必再写。

### Prompt Cache 与决策冻结（本层隐藏的关键坑）

- 坑：某个 40K 结果第 5 轮"没超单条阈值、保留原文"，到第 15 轮聚合总量超限、按规则应被替换 → 替换使**消息前缀变化 → Anthropic Prompt Cache 失效** → 每轮都要重处理数万~十几万 token 前缀，延迟与成本上升。
- 解（MewCode 采用、Claude Code 同款）：维护 `ContentReplacementState`，记录每个 `tool_use_id` 的替换决策，**决策一次冻结**：
  - 决定「不替换」→ 整个会话永远保留原文、不再评估；
  - 决定「替换」→ 之后每一轮都用**同一串** preview 原文重放（不重新生成），保证前缀逐字节一致。
- 每轮把工具结果分三类：已替换的（缓存 preview 重放）/ 已决定不替换的（保留原文跳过）/ 新产生的（评估后冻结）。
- 三轮走查（设单条预算 20K；X=8K、Y=7K、Z=9K）：state 两本账 `seenIds`（问过的 id）+ `replacements`（被替换 id → preview 串）。
  - R1：X 未问过 → 8K≤20K 不替换，记 `seenIds`。模型看到 X 原文。
  - R2：X 命中 seenIds 且不在 replacements（=已判"不替换"）→ 跳过；Y 新候选，15K 仍不超，记账。前缀与 R1 一致 → cache 命中。
  - R3：X/Y 冻结跳过；Z 新候选，8+7+9=24K>20K 需替换一个 → 只能动 Z（X/Y 一变前缀就漂、整条 cache 失效）→ Z 写盘、生成 preview 入 `replacements`。
  - R4 起 X/Y/Z 永不再变，前缀逐字节稳定，cache 一路命中。
- 启示：**上下文管理不仅要算"保留什么信息"，还要算"改动前缀的代价"**。每轮天真地重新评估所有工具结果，等于 prompt cache 命中率归零。

## 第 2 层：全量摘要 Auto-Compact（治疗·高成本·最强压缩）

- 手段：调用 LLM 生成一份结构化摘要替换旧消息。贵（额外一次 API）、有信息损失，但能把十几万 token 压到几千。
- **触发阈值**（每轮循环开始时检查）：`阈值 = 窗口 − 20,000(预留给摘要输出) − 13,000(安全余量)`。
  - 200K 窗口 → 180K − 13K = **167K** 触发；1M 窗口 → 980K − 13K = **967K**。
- **为什么固定值、不用百分比**：buffer 防的是"单轮波动"（读一个文件 ~15K token、一条命令几百~几千 token，量级固定），风险大小取决于单次工具结果、与总窗口无关。
  - 90% 方案：200K 只剩 20K buffer（刚好够一次大文件），1M 却留 100K（浪费，够装 7 个大文件）；
  - 98% 方案：200K 只剩 4K（一次普通文件读取就撞墙），1M 留 20K 才刚好。
  - 33K（20K+13K）固定 buffer 在任何窗口下恰好够"挡住一到两次大工具调用"，没有百分比能同时适配所有窗口。
- **20K 给摘要输出**：摘要有 9 个结构化部分 + 草稿块，复杂会话输出约 15–18K token，留 15K 有截断风险；预留 50K 则有效窗口缩到 150K、压缩过早触发（137K），而摘要长度由对话复杂度决定、不会因给更多空间而变长，多留纯浪费。
- **13K 安全余量**：≈一个大源文件的 token 量，防两次检查之间一个意外偏大的工具结果直接撞墙；配合第1层，能渗进上下文的单轮增量基本在万 token 内，13K 够盖住波动。
- **手动 /compact 余量只有 3K**（比自动的 13K 小得多）：用户主动触发=知道自己要干嘛，不需要那么大反应空间。
- 三个数（20K / 13K / 3K）共同点：由**单轮操作特征**决定、不由窗口总量决定，所以是固定值。

### 摘要 Prompt 设计（直接决定压缩后表现）

- 要求生成**结构化摘要，明确 9 个部分**：
  1. 主要请求和意图（用户到底想做什么）
  2. 关键技术概念
  3. 涉及的文件和关键代码段（保留关键片段）
  4. 错误和修复
  5. 问题解决过程
  6. **所有用户消息——尽量原文保留**
  7. 待办任务
  8. 当前工作（要最详细）
  9. 可能的下一步
- 第 6 条为何原文：改写下丢失意图/偏好/语气。例："不要用 interface{}，用 any" 被摘要成"偏好现代语法"，模型下次可能给出 `type any = interface{}`。空间不足时 LLM 自行取舍，这条本质是**优先级指引**而非硬性全量。
- **两阶段生成**：先产出 `analysis` 草稿块梳理发生了什么，再产出正式 `summary` 块；最终**只保留 summary、丢弃 analysis**。实验证明"先梳理再写"摘要质量显著更高，中间产物不留。
- **禁止工具调用**：摘要调用复用了原对话消息上下文，工具定义随消息一起传入、模型仍"看得到"工具。两种做法：
  - MewCode：调摘要 API 时**直接不传 `tools`**（模型彻底看不到，自然不调）；
  - Claude Code：保留 `tools`（少一次重组消息的开销），靠 prompt 硬拦——禁令出现两次，开头一次、结尾再强调一次（"提醒：不要调任何工具，工具调用会被拒绝，你会失败"）。
- 摘要质量差的连带风险：压缩后 Agent 忘关键细节 → 需要"压缩后恢复"补。

### 压缩后恢复（摘要替换旧消息后，重新附加关键上下文）

- 最近访问的文件：最多恢复 5 个、每个最多 5,000 token；
- 技能定义：若之前用过 Skill，重新注入，总预算 25,000 token；
- 工具列表：重新声明全部可用工具（保证摘要后首次请求仍带完整工具定义）；
- **压缩边界消息**：一条特殊消息告诉模型"以上是摘要；需要具体文件内容请重新 ReadFile 读取，不要靠摘要猜测代码细节"——防止根据"修复了 handler.go"这类模糊描述脑补出不存在的代码。
- 压缩后消息序列示意：`[system]` → `[user]` 摘要 → `[assistant]` 边界消息 → `[user]` 恢复文件×n → 最近若干条原文消息完整保留。

### 熔断与极端自救

- **熔断**：全量摘要因网络 / API 错误 / PTL 等**连续失败 3 次 → 停止自动触发**，交用户手动处理。防"上下文已超限→每轮触发→每轮失败→死循环"。
- **摘要请求自身 PTL** 的重试逻辑：把消息按 API 轮次分组 → 丢弃最旧的几组 → 用剩余消息重试，最多重试 3 次；还不行就丢 20% 的消息组再试。
- **紧急压缩 ForceCompact**：正常对话请求返回 `prompt_too_long`（说明阈值没挡住：估算偏差 / 某轮异常大结果跳过检查）→ Agent Loop 捕获该错误 → 立刻触发一次压缩 → 用新消息列表**重试原请求一次**；仍超则按正常错误流程，不无限重试。定位：自动压缩=预防，紧急压缩=治疗兜底，让 Agent 不至于因一次估算偏差整体瘫掉。

## 手动 /compact

- 两个典型场景：预防性压缩（知道接下来要读大量文件、提前腾空间）；话题切换（清掉上一个 bug 的细节噪声再做新任务）。自动检查点之间用户也可随时触发。

## 两层协作关系（每次调 API 之前的顺序）

1. `applyToolResultBudget`：检查**新产生**的工具结果是否超限（单条 >50K / 聚合 >200K）→ 该存盘存盘。管"单条消息大小"，**预防性**。
2. `autoCompact`：检查整体是否逼近窗口上限（167K…）→ 超了就全量摘要。管"对话累积长度"，**治疗性**。

- 对照场景：连续读 20 个小文件（单文件均 <50K，第1层无动作）→ 累计逼近 167K → 第2层把 20 轮压成几千 token；一条 80K 字符命令日志 → 第1层存盘留 2K 预览 → 总量远未到阈值，第2层不触发。
- 趋势观点（原文小结）：早期 Coding Agent 在上下文管理上叠了很多层（裁旧消息、清过期工具输出、读时投影压缩等），随窗口变大、模型变强，趋势反而是**层数越来越少**，留下的就是这两层。自研 Agent "先用存盘挡大结果，再全量摘要兜底长对话"即够。

## 对 ACode 的借鉴（假设，供后续 spec/tasks 落定时参考）

- 现状（本文件上方 FlashMemory 摘记提过）：超限裁最旧（Recency Only 语义），模型不知情，长会话会静默丢远距决策。8-1 给了完整得多的客户端替代形态：两层压缩 + 恢复 + 熔断 + ForceCompact + 决策冻结。
- 与 prompt.md 诉求对应：`Token预算` = 第2层"每次调 API 前估算"环节（近似即可，原文也按字符粗算）；`大结果存磁盘` = 第1层；`全量摘要(auto-compact)` = 第2层 + 压缩后恢复；`手动 /compact` = 手动节。"不做精确 tokenizer"与原文粗算口径一致。
- 值得抄的四个设计约束（若与 ACode 现状冲突，以架构现实权衡）：
  1. 阈值用**固定值**（窗口 − 20K − 13K），不随窗口百分比走；若要支持多种窗口大小做成配置，仍是固定余量；
  2. **决策冻结**保住前缀逐字节不变，以利用 prompt cache——替换类操作勿每轮重评；
  3. 摘要里**用户消息尽量原文保留** + 压缩后插**边界消息**防模型脑补；
  4. 自动压缩(预防) + **ForceCompact(治疗)** + **熔断(连败3次停止)** 三者同上；只靠阈值挡，会因估算误差一次就瘫。
