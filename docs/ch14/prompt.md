# Agent Teams —— 从一次性子任务到长期协作团队

> 让主 Agent 从「派临时工」升级到「带一个团队」：队员能并行、能互相说话、能自己认领活

> 前言：本章对应教材站点第 15 章（agent-docs `chapter-15-*`）。教材里的项目叫 MewCode，本文一律换算成 ACode 的讲法。教材站点第 13 章（SubAgent）对应我们的 `ch12`，第 14 章（Worktree）对应我们的 `ch13` —— 本章建立在它们之上，凡是还没落地的地方都会显式标「待补」。

## 为什么需要它

上一章我们让主 Agent 学会了一件事：**把活派出去**。派一个子 Agent 到干净的上下文里干活，干完把结果收回来。加上 Worktree 那章给每个子 Agent 配了独立的工作目录，`帮我做个安全审查` 这类任务已经很顺了。

但这类任务有个共同形状：**派出去 → 等结果 → 拿回来**。一条直线。

真实的活儿不总是直线。

### 场景一：四个模块，串行改了二十分钟

你让 Agent 重构一个东西，涉及四个模块。

它派一个子 Agent 去改模块 A，改完返回。再派一个去改 B，改完返回。然后 C，然后 D。

四个模块串行改完，二十分钟过去了。

可只要看一眼依赖就明白了：**A 和 B 互不依赖，C 依赖 A 的结果，D 依赖 B 的结果**。如果 A 和 B 能同时开工，C 在 A 完成后立刻接着上，D 在 B 完成后接着上，总时间能砍掉将近一半。

为什么没这么干？因为 SubAgent 模型里，**主 Agent 一次只能等一个活**。它派出去，然后阻塞着等这个结果回来，才轮到派下一个。它没有「同时盯着几个活」的位置——不是不想并行，是结构上没这个位子。

### 场景二：发现了线索，却没法直接告诉同事

换个场景。你让 Agent 调查一个诡异的 bug。理想情况下你会希望三路人马同时开工：一个查日志，一个读代码，一个检查配置。

查日志的 Agent 发现一条可疑记录，它需要说一句话：

> 你去看一下 `handler.java` 第 47 行，那里有个条件判断可能是问题根源。

在 SubAgent 模型里，**这句话说不出去**。

子 Agent 只能跟主 Agent 说话：干完了，把结果交回去。子 Agent 之间没有任何通道，彼此看不见。所有信息必须绕着主 Agent 中转一圈。

主 Agent 于是成了整个系统的瓶颈。这就像**一个团队里所有人只能跟经理汇报，同事之间不能直接说话**。三个人以内还能凑合，任务一复杂、人一多，经理就变成一个纯粹的信息交换机，效率断崖式下跌。

### 场景三：包工头自己还在下工地

还有个更隐蔽的问题。

主 Agent 派完队员之后，**自己手里还留着全套工具**。它一边协调，一边顺手用 ReadFile 看代码、用 Bash 跑命令、甚至自己动手改文件。

人少的时候没事。但任务一复杂：

- 它自己在主仓库的目录里改代码，和队员的修改**直接冲突**
- 它的上下文窗口已经被任务列表、队员状态、消息记录占掉一大块，再往里塞代码内容，**调度用的信息和自己干活的信息互相干扰**

一个同时管项目和写代码的技术负责人，两件事都做不好。这个类比不是修辞，它就是这一章最后要解决的工程问题。

### 一句话说清三者的区别

| | 解决什么 |
|---|---|
| SubAgent（上一章） | **上下文隔离** —— 子任务的中间过程不污染主上下文 |
| Worktree（上一章） | **文件隔离** —— 各自改各自的目录，工作在过程中不打架 |
| Agent Teams（本章） | **多 Agent 协调** —— 谁能并行、谁和谁对接、活到什么程度了 |

前两章解决的是「别互相踩」，这一章解决的是「一起干」。

## 先从比喻说起：外包 vs 正式团队

理解这一章最快的办法，是先分清两种「用人方式」。

**SubAgent 像外包。** 你把需求发过去，它交付成果，结束。中间不用沟通，出了事也不用开会。它拿到的是一张明确的工单，交付的是一个明确的结果。用完这次的上下文就扔了，下次有事重新找人、重新讲一遍背景。

**Team 队员像正式员工。** 它能**看看板**（有哪些任务、谁在做、做完了没），能**认领任务**（而不是等人派），能在群里 **@同事**（发现接口变了直接通知下游），甚至**自己拆子任务**。

这个差别不是修辞，它是**工具集上的硬差别**。队员手里多了一组主 Agent 和普通子 Agent 都拿不到的工具：

```
队员专属协作工具：
    TaskCreate    创建任务
    TaskGet       看任务详情
    TaskList      列所有任务
    TaskUpdate    更新任务状态（含依赖字段）
    SendMessage   给其他队员发消息
```

普通子 Agent 没有这些，主 Agent 也没有。就像外包人员拿不到公司的 Jira 和 Slack 账号一样——**不是不让他用，是系统里根本没有这个入口**。

这一点很关键，它是上一章那条设计哲学的直接延续。上一章我们说过「**能力边界优于行为约束**」：与其在提示词里写「请不要修改文件」，不如根本不给它写文件的工具。这里同理——与其叮嘱队员「你们要好好协调」，不如**把协调能力作为一个工具包发下去**，不给的人自然就协调不了。

## 拓扑变了：从星型到网状

这是本章最本质的一句话。

**SubAgent 是星型拓扑。** 主 Agent 在中心，子 Agent 在四周。所有通信必须穿过中心。子 Agent 之间没有边。

**Agent Team 是网状拓扑。** 每个队员有自己的上下文窗口，可以直接给某个队友发消息，不必再绕回 Lead 中转。

```
    星型（SubAgent）                网状（Team）
        主                             alice ── bob
      ╱ │ ╲                            │  ╲  ╱ │
   子A 子B 子C                         │   ╳   │
                                       │  ╱ ╲  │
                                      carol ── lead
     子之间看不见彼此                    谁都能直接找到谁
```

这里要先把一个细节说破，免得你后面产生错误的期待：**所谓「直接发消息」不是网络层面的实时直连。**

底层走的是「**共享文件邮箱 + 轮询**」。消息写进一个文件，收件人在自己下一轮 Agent Loop 的**开头**把它读出来。中间隔着一次轮询间隔（教材里是几百毫秒级）。

所以准确的说法是：**队员之间可以直接寻址，但通信本质上是异步的**。

这不是偷懒。它换来的是三种后端（下面会讲）能用**同一套**通信机制——不管队员是独立进程还是同一个进程里的协程，收消息走的都是同一个文件邮箱。一套机制跑三种部署形态，这个性价比很高。

**共享任务列表 + 异步邮箱，就是整个 Team 的协调底座。** 整章剩下的内容，基本都是在讲这两样东西怎么用、怎么不出错。

## 和业界框架的关系：去中心化协调 vs 中心化编排

你可能会想：多 Agent 协作这事，AutoGen、CrewAI、LangGraph 早就在做了，ACode 这套算什么？

差别在**「谁来决定谁在什么时候做什么」**。

| 框架 | 决策权在哪 |
|---|---|
| AutoGen `GroupChat` | 一个调度者按规则决定下一句该谁说 |
| CrewAI | 一个 `Crew` 对象编排整个任务流转 |
| LangGraph | 干脆把协作写成一张状态机 |
| **ACode Team** | **框架不裁决。协调能力以「工具」形式发给每个队员，由 LLM 自己看着办** |

前三条路线都把编排决策收在框架里；ACode 走的是反方向——**没有调度器**。

代价是行为可预测性弱一些：你不会拿到一张确定的执行图，实际怎么走取决于 LLM 每一轮的判断。

收益是：**想新增一种协作方式，只需要加一个工具，不需要动调度器**。

这个取舍是本章的骨架，后面讲协调机制和 Coordinator Mode 时会反复撞见它。

## 团队的核心结构

组建一个项目小组，最少需要三样东西：一个**组名**、一个**负责人**、一本**花名册**。

Agent Team 的数据结构就是这三样的直接映射：

```
AgentTeam:
    name         团队名称
    leadAgentID  谁是负责人
    members      花名册
    configPath   持久化位置
```

花名册里每个人长这样：

```
TeammateInfo:
    name              队员名称（由 Lead 分配）
    agentID           对应的 Agent 实例 ID
    agentType         用哪个 Agent 定义创建
    model             模型，可覆盖
    worktreePath      所在的 Worktree 路径
    backendType       跑在哪里：tmux / iterm2 / in-process
    isActive          活跃状态（可选）
    planModeRequired  是否需要 Lead 审批
```

逐个看几个容易误解的字段。

### `backendType` 是**每个队员**独立决定的

同一个团队里，队员 alice 可以跑在独立进程里，队员 bob 可以跑在同一个进程内。

你可能会以为「后端」是团队级的配置——开团队的时候选一次，全队统一。**不是**。它是 member 级的字段。这个设计让「这个活重、给它单独的进程」和「这个活轻、塞进主进程就行」能同时成立。

### `isActive` 为什么是一个 boolean，而不是三值枚举

直觉上这里应该是个枚举：`active` / `idle` / `terminated`。

实际设计只有一个可选 boolean：`undefined` 或 `true` 表示活跃，`false` 表示空闲。

**没有 `terminated`。** 队员终止之后，直接从 `members` 列表里**移除**，不留墓碑。

想清楚这个选择就不奇怪了：列表里有的，就是活的或暂停的；列表里没有的，就是不存在。**「存在性」本身承载了「已终止」这个信息**，不需要再拿一个状态位重复表达一遍。

好处是清理逻辑变得极简——不用写「把状态置为 terminated 但保留记录」这种半死不活的中间态。

### `worktreePath` 是上一章的延续

每个队员工作在自己的 Git Worktree 里，文件系统完全隔离。

这一章**不负责**实现工作树本身（那是 `docs/ch13/` Worktree 章的事——设计稿已出，代码待落地）。它只是**消费**这个能力：花名册里记一笔「这个队员的活儿在哪个目录」。

所以本章能讲到什么程度，取决于 Worktree 章落地到什么程度。这一点在下面的「边界」里再展开。

### `planModeRequired`：给高危队员加一道审批门槛

这个字段让 Lead 可以给特定队员加一道锁：**这个队员在执行任何修改操作之前，必须先提交一份计划给 Lead 审批，批了才能动手。**

适合哪类？风险较高的修改任务。你信得过 alice 读代码，但不太放心它直接改认证模块——那就把它的 `planModeRequired` 打开。

这是「权限」这个概念从**用户对 Agent** 扩展到 **Lead 对队员**的一层。

### Lead 不是新角色，就是主 Agent 自己

这一点容易搞混。**Team Lead 就是当前的主 Agent 本身。**

你对 ACode 说「创建一个团队来做这件事」，主 Agent 就自动承担起 Lead 的角色——负责建团队、派生队员、分解任务、协调进度、最后收口。

所以这一章不是「引入了一个新的 Agent」，而是「**主 Agent 多了一个身份**」。

## 为什么团队要有独立顶层工具

上一章的 `Agent` 工具用一个统一接口搞定了子 Agent 的创建和运行。到了团队模式，复杂度上了一个台阶：

- 团队本身有生命周期（创建、运行、清理）
- 队员的派生必须关联到某个具体团队
- Lead 在团队存续期间可能还要进入一个特殊的协调模式

如果把这些全塞进 `Agent` 工具的参数分支里，这个工具就变成一个什么都干的巨型开关了。

所以团队模式引入了**独立的顶层工具**：

```
// 第一步：创建团队
TeamCreate(team_name="refactor-auth", description="重构认证模块")

// 第二步：往这个团队里派队员
Agent(subagent_type="worker", name="alice", prompt="重构数据层")
Agent(subagent_type="worker", name="bob",   prompt="重构服务层")
```

职责切得很干净：**`TeamCreate` 建团队，`Agent` 的 `team_name` 参数往已有团队里加人。**

`TeamCreate` 自己做的事情其实不多：检测执行后端、创建团队配置文件、初始化共享任务列表、把 Lead 注册进团队。但它值得作为一个独立工具存在，理由很直白——

> **团队的创建是一个有明确边界的操作，它会改变 Lead 的运行模式，不应该作为 `Agent` 工具的副作用偷偷发生。**

同名团队已存在时，系统自动在名字后面追序号（`team` → `team-2` → `team-3`）避免撞车，而不是报错打断用户。

对应地还有一个 `TeamDelete` 负责拆团队。它的实现思路是「**删除 = 停掉所有人然后清理**」，不要求用户先手动把每个队员停一遍。返回结果里带上被停掉的队员数量和名字，给 LLM 一个明确的反馈。

## 三种执行后端

在讲协调机制之前，得先解决一个更基础的问题：**队员跑在哪？**

三种选择，对应 `BackendType` 的三个取值：

| 后端 | 队员在哪 | 隔离强度 | 依赖 |
|---|---|---|---|
| `tmux` | 独立的 tmux pane（一个完整 CLI 进程） | 强 | 有 tmux |
| `iterm2` | 独立的 iTerm2 split pane（完整 CLI 进程） | 强 | macOS + iTerm2 + it2 CLI |
| `in-process` | 同一个进程内的独立协程 | 弱 | 无 |

### 进程后端：完整的隔离

tmux 后端的做法是：给每个队员开一个新 pane，在 pane 里启动一个**完整的 CLI 实例**。

```
function spawnTmuxTeammate(team, name, config):
    paneID = tmux.splitWindow(team.name + "-" + name)   // 开一个新 pane
    tmux.sendKeys(paneID, buildCLICommand(config))       // 在 pane 里拉起 CLI
    // 队员之间通过 mailbox 文件通信
```

好处是**完全隔离**：每个队员是独立进程，有自己的内存空间和配置；一个崩溃不影响其他；生命周期也不依赖 Lead（Lead 退出了，队员还活着）。

因为是完整 CLI 实例，pane 里的队员**拥有 `Agent` 工具**，可以自己再派子 Agent——同步的、后台的都行。

但有一条硬限制：**所有队员的 `team_name` 参数被屏蔽，队员不能 spawn 其他队员。**

这条限制的目的很明确：防止队员自行扩张团队。如果每个队员都能建团队、拉人，团队规模会指数级膨胀，Lead 再也搞不清谁是谁。**往团队里加人的权力，只属于 Lead。**

### 进程内后端：轻量，但绑在 Lead 身上

如果环境里既没有 tmux 也没有 iTerm2，就落到 `in-process`：

```
function startInProcessTeammate(team, name, config):
    tools = buildTeammateTools(baseTools, team)   // 注入协调工具
    agent = createAgent(config, tools)
    runAsync:
        agent.runToCompletion(context, initialPrompt)
```

轻量、启动快、不依赖任何外部工具。代价是限制更多：

- **生命周期绑在 Lead 身上**——Lead 退出，所有 in-process 队员一起消失
- `Agent` 工具虽然可用，但**只能派同步子 Agent**；后台 Agent 和「spawn 队员」都被禁止

### 怎么选：一次决定，四个判断

检测逻辑只看四件事，按优先级从上往下走：

```
1. 已经在 tmux 里？        → 用 tmux（哪怕是从 iTerm2 里打开的 tmux 也算）
2. 在 iTerm2 里？          → 用 iTerm2 原生 pane
3. 本地装了 tmux 二进制？   → 拉一个外部 tmux session
4. 以上都不是              → in-process
```

**in-process 是兜底选项**：只要环境支持 pane 后端，系统就优先用 pane；没有 pane 才退到 in-process。

这里有一个容易被误解的地方值得说清楚：**所有选择都在 spawn 开始之前由 `detectBackend` 一次性决定**。

- 没有专门的「非交互模式」分支
- 没有「pane spawn 失败了再切 in-process」的运行时回退

所以如果你发现系统用了 in-process 而你不希望这样，处理办法只有一个：**在工具链层面把 tmux 装上，或者把当前会话切进 iTerm2**。指望它自动升级到 pane 后端是等不到的。

## 协调机制：共享工具取代共享文件

多个 Agent 并行工作，最大的挑战是协调。三个问题：

**谁做什么？做到哪了？要传什么信息？**

上一章的子 Agent 是通过后台任务管理器管理的。这一章在此之上，给队员额外注入一组**协调工具**——就是前面说的那五人组：`TaskCreate` / `TaskGet` / `TaskList` / `TaskUpdate` / `SendMessage`。

其中前四个是**共享任务工具**，提供团队级的任务管理（创建、查看、列举、更新），并且支持 `addBlocks` / `addBlockedBy` 依赖字段。

真正的新成员是 **`SendMessage`**——它让队员之间第一次有了直接通信的能力。

### `SendMessage`：队员之间的直接通信

场景：alice 在改模块 A 的时候发现一个接口签名变了，而 bob 正在改模块 B 里调用这个接口的地方。

如果 alice 不吱声，bob 就会照着**旧的接口**写代码，等最后合并的时候才发现编译不过——前面所有工作白做。

`SendMessage` 让 alice 能直接说一句：

```
SendMessage(to="bob", summary="接口签名变更通知",
            message="Authenticate() 的签名改了，多了一个 ctx 参数")
```

#### `summary` 这个字段为什么必须有

发纯文本消息时，**必须**带一个 5～10 个词的摘要。

为什么？因为 `summary` 会作为消息预览显示在 UI 上，让 Lead 和其他队员**扫一眼消息列表就能知道每条说了什么**，不需要逐条展开。

这不是格式洁癖。在一个十几个队员、几百条消息的团队里，「能不能快速扫」直接决定了 Lead 还能不能有效地调度。**摘要字段是给协调者省注意力的。**

#### `to` 支持两种寻址

**第一种：队友名称或 Agent ID。**

```
to="bob"          按名字
to="agent-a1b"    按 ID
```

两者路由到同一个地方。用名字是为了可读；用 ID 是因为系统发给 Lead 的任务通知里返回的就是 ID，续写的时候直接拿来用最省事。

如果目标 Agent 已经停止了，**系统会自动从磁盘把它恢复起来**（下面「空闲与续写」会展开讲）。

**第二种：广播 `to="*"`。** 发给所有队友，适合通知全团队的变更。

#### 结构化消息：不靠自然语言猜

除了纯文本，`SendMessage` 还支持几种**协议化**的消息类型：

| 类型 | 含义 | 谁能发 |
|---|---|---|
| `shutdown_request` | 请求某个队员优雅退出 | 任何人 |
| `shutdown_response` | 对退出请求的回复（同意 / 拒绝 + 理由） | 只能发给 Lead |
| `plan_approval_response` | Plan 模式的审批回复（通过 / 驳回 + 反馈） | 只有 Lead 能发 |

为什么要把这些做成结构化消息，而不是让它们用自然语言说？

因为这是**生命周期和权限审批**——是**执行动作**的事件，不是「商量一下」的事件。让队员之间靠「理解自然语言」来协调关闭和审批，模糊性太高：一句「你差不多可以收了」到底算不算批准退出？**协议化把这个模糊性直接消掉。**

#### Plan 审批工作流

`plan_approval_response` 值得单独说一下流程。

Lead 把某个队员的 `planModeRequired` 设为 `true` 后：

```
1. 队员分析任务 → 生成执行计划
2. 计划通过 mailbox 发给 Lead
3. Lead 审阅
4. Lead 用 plan_approval_response 回复
     通过 → 直接放行
     驳回 → 可附反馈，例如 feedback: "不要改 handler 层，只改 service 层"
5. 审批通过后，Lead 的权限模式传递给队员
     （Lead 在 default 模式下，队员也切到 default 开始执行）
```

#### 消息是怎么送到的：名称注册表 + 邮箱文件

路由分两段。

**第一段：名称 → ID。** 靠一张 `agentNameRegistry` 表。`Agent` 工具有一个 `name` 参数，非空时系统会把 `name → agentId` 的映射注册进去。队员创建时都带名字，所以自动完成了注册。

**第二段：按后端投递。**

```
agentID = agentNameRegistry.resolve(to)     // 名称解析成 ID，解析不到就报错
msg = new MailboxMessage(from, to, content)
mailbox.write(agentID, msg)                 // 写进目标队员的收件箱文件
if isTmuxTeammate(agentID):
    tmux.sendKeys(agentID, "")              // 额外敲一下 pane，把对方叫醒
```

两种后端的差别：

- **Pane 后端**（tmux / iTerm2）：写 mailbox，**再额外 `send-keys` 唤醒**目标 pane。因为独立进程不会自动去看文件，得敲一下提醒它。
- **in-process 后端**：只写 mailbox。目标队员在**每轮 Agent Loop 开头**先把未读消息读出来，注入成 system reminder，下一次调 LLM 时自然就看到了。

广播的话，`to="*"` 就走「发给所有队友」的分支，不查注册表。

#### 并发写邮箱会不会撞车

后端工程师看到「文件当邮箱」这个方案，第一反应通常是这个。

处理方式是**给每个收件箱单独配一个 lock file**：

```
写之前：用 O_CREATE | O_EXCL 抢锁（"创建文件"本身就是原子操作）
抢不到：按 5～100 毫秒随机抖动后重试，最多 10 次
        （随机化是为了避免多个进程同步重试导致活锁）
超时：  超过 10 秒还没释放的锁，认定为 stale，直接删掉
        （防止某个崩溃的进程留下永久死锁）
拿到锁：整文件读出来 → 改 → 整文件写回去（原子替换，不做追加）
```

有一个细节设计得挺巧妙：**in-process 和 pane 后端共用同一套文件锁机制**。也就是说，哪怕所有队员都跑在同一个进程的协程里，它们之间的并发也是由**文件锁**串起来的，不需要再额外维护一套内存锁。

一套锁机制覆盖两种部署形态，代码路径就只有一条。

### 什么时候用 `SendMessage`，什么时候用 `TaskCreate`

这个判断其实你在公司里天天在做。

- 「**帮我检查一下配置文件**」→ 你会**开一个工单**。因为你要**追踪它做没做**。
- 「**我改了接口签名，你注意一下**」→ 你在**群里说一声**。因为它就是个 FYI，不需要追踪状态。

**前者是任务，后者是消息。**

判断标准就一条：**这件事需不需要「状态」**。需要「谁在做 / 做完了没」的，用 Task；只是「通知一声」的，用 SendMessage。

## 团队的生命周期

前面讲的是零件，现在用一个完整场景把它们串起来。

假设你对 ACode 说：

> 帮我重构认证模块，数据层和服务层要分开改，改完跑一遍测试。

ACode 判断这个任务值得组个团队来做，于是开始走五步。

### 第一步：创建 —— 先把摊子支起来

建团队配置文件、检测执行后端、把 Lead 自己注册进去。

```
function createTeam(lead, name) -> AgentTeam:
    team = new AgentTeam(name: name, leadAgentID: lead.id,
                         members: [], configPath: ...)
    writeJSON(team.configPath, team)
    return team
```

团队配置持久化到 `.acode/teams/{name}/config.json`，一个团队一个目录。

### 第二步：分解 —— Lead 把活掰开了排好

这一步**完全是 Lead 作为 LLM 自己推理出来的**：分析用户目标，判断哪些事可以并行、哪些有先后依赖，然后把任务写进共享列表。

对「重构认证模块」这个例子，Lead 会创建四个任务：

```
T1 重构数据层    T2 重构服务层    T3 更新测试    T4 更新 API
```

然后标记依赖：T3 等 T1，T4 等 T2。最后派 alice 和 bob 分头干活。

依赖关系有两种表达方式，**两种经常混用**。

**方式一：系统级依赖（结构化）。**

`TaskUpdate` 提供 `addBlocks` 和 `addBlockedBy` 两个字段，建立结构化的依赖图：

```
// T2 被 T1 阻塞：T1 完成前 T2 不应该开始
TaskUpdate(taskID="2", addBlockedBy=["1"])

// 反过来表达同一件事：T1 阻塞了 T2
TaskUpdate(taskID="1", addBlocks=["2"])
```

这两个字段接受任务 ID 数组，系统会在任务之间建立**有向依赖关系**。队员通过 `TaskList` 能看到每个任务的依赖状态，知道**哪些被阻塞、哪些可以认领**。

**方式二：文本约定（自然语言）。**

简单场景下，Lead 直接把依赖写在任务描述里——「需要在 T1 完成后再开始」。队员读描述自己判断顺序。

这就像 GitHub Issues 里用文字写 `blocked by #42`：**系统不强制阻止你去点开始，但约定让协作者知道先后**。

实践中的分工很清楚：**核心依赖用 `addBlockedBy` 建立系统级约束，补充说明用描述文本传达意图。**

#### 派队员：六个步骤

```
1. 加载 Agent 定义（指定了 model 就覆盖默认值）
2. 创建 Worktree，命名规则 team-{teamName}/{name}
3. 调 buildTeammateTools，把协调工具注入基础工具集
4. 按后端分流：pane 后端走 spawnPaneTeammate，in-process 走 spawnInProcessTeammate
5. 把队员名称注册进 agentNameRegistry（这样 SendMessage 才找得到它）
6. 构造 TeammateInfo，注册到 team.members
```

第 4 步注意：**后端类型可以是 per-member 的**，同一个团队里不同队员可以用不同后端。

第 2 步里队员创建时**自动获得一个 Worktree**——这是上一章（`docs/ch13/`，设计稿已出、代码待落地）的能力。

队员的创建也分两种模式，和上一章一样：

- 指定 `agentType` → **定义式**，从空白上下文开始，适合职责明确的角色
- 留空 → **Fork 式**，继承 Lead 的完整对话历史，知道用户的需求背景

（Fork 路径受 `FORK_SUBAGENT` 开关控制。开关没开时，省略 `agentType` 会落到默认的 `general-purpose` agent，而不是 fork。）

#### 让一个子 Agent 变成队员，只差两件事

1. **往工具集里注入协调工具**（上面第 3 步）
2. **往系统提示里追加一段团队通信的说明**

第 2 件事值得单独讲，因为**它的长度和直觉相反**。

你可能会想：既然是团队成员了，总得把花名册、协调工具的用法、推荐工作流程都写进系统提示吧？

**不用。** 工具列表本身就是自描述的——LLM 看到 `TaskList`、`SendMessage` 这些工具的名字和描述，自然知道怎么用。系统提示写一大段反而是重复劳动，还会占上下文。

附录**只需要解决一个问题**：

> **告诉队员：你的纯文本回复对队友不可见，想通信必须用 `SendMessage`。**

这就是为什么这段附录只有三行：

```
IMPORTANT: You are running as an agent in a team.
Just writing a response in text is not visible to others
on your team - you MUST use the SendMessage tool.
The user interacts primarily with the team lead.
Your work is coordinated through the task system
and teammate messaging.
```

三条规则：用 `SendMessage` + `to: "<name>"` 给指定队友发消息；用 `to: "*"` 广播（谨慎使用）；**纯文本回复对队友不可见，必须用 SendMessage**。

至于具体的工作流程——谁先做什么、怎么交付——**由 Lead 通过 prompt 和任务描述来传达，不硬编码在系统提示里**。同一个团队底座，配上不同的任务，就是不同的工作流。

### 第三步：执行 —— 队员自己跑

队员派出去之后，每个队员就是**一个普通的 Agent 实例**，在自己的 Agent Loop 里自主决定做什么。

它的工具集 = 干活的工具（`ReadFile` / `WriteFile` / `Bash` …） + 协调工具（`TaskCreate` / `TaskList` / `TaskUpdate` / `SendMessage`）。

于是一个队员典型的一轮可能是：

```
TaskList      →  看看有什么任务可做
ReadFile / WriteFile  →  干活
（中间从 mailbox 收到队友消息）
TaskUpdate    →  更新任务状态
```

**整个过程由 LLM 的推理驱动，和主 Agent 处理用户请求的方式完全一样。** 系统不会额外注入固定的调度指令。「什么时候该查消息、什么时候该认领任务、什么时候该给队友通气」——**LLM 自己判断**。

协调工具和 `ReadFile`、`Bash` 一样，只是工具列表里的一个选项。**Agent Loop 对它们不做任何特殊处理。**

这里有两点要说明。

**第一，任务状态管理依赖 LLM 的判断。** `TaskList` 展示的任务带状态标记，LLM 能看到哪些已完成、哪些在进行。系统提示引导队员按合理顺序推进。

**第二，也是更重要的一点：系统没有把任务 assign 给队员，而是让队员自己从列表里选。**

为什么？因为**这比 Lead 强制分配更灵活**。队员基于自己的上下文做选择——alice 刚读完数据层的代码，自然倾向于挑数据层相关的任务，因为它手里正握着这块上下文。强行分配反而丢掉了这个信息。

### 第四步：收敛 —— 把大家的成果拢到一起

所有任务标成 completed，轮到 Lead 重新登场。

每个队员在自己的 Worktree 里改了一堆代码，现在要把这些修改**合并回主分支**。

这里的关键设计是：**合并也是 LLM 推理驱动的，不是脚本驱动的。**

Lead 通过 `Bash` 执行 git 命令，通过 `ReadFile` 检查冲突文件，通过自己的判断决定合并顺序和冲突解决策略：

```
// 1. 依次合并每个队员的 Worktree 分支
git merge worktree-team-refactor-auth+alice --no-ff -m "merge: alice"

// 2. 有冲突就读取冲突文件，尝试解决
git add -A
git commit -m "merge(alice): resolve conflict"

// 3. 搞不定的冲突，回滚并上报用户
git merge --abort
→ 向用户报告：alice 的修改和 bob 的有逻辑冲突，需要你来决定
```

**为什么不做成自动化？**

因为**合并冲突的解决本质上是语义理解**——你得知道两边改动的**意图**，才知道哪个该留、怎么揉在一起。这恰好是 LLM 擅长的事情。

大部分机械性冲突（比如两边在文件的不同位置各加了新代码），Lead 能自己搞定。只有涉及**逻辑矛盾**、Lead 判断自己没把握选对的时候，才会暂停合并、把冲突上下文报告给用户，让用户做最终决定。

**这个「能搞定的自己搞定，搞不定的退回给人」的分寸，是收敛阶段的设计核心。**

### 第五步：清理 —— 拆掉脚手架

活干完了，收拾工地：终止队员、删除 Worktree、清理任务文件和团队目录。

```
function cleanup(team):
    // 1. 先确认所有队员都已空闲，否则拒绝清理
    for teammate in team.members:
        if teammate.isActive != false:
            return error("队员 " + teammate.name + " 仍在活跃中")
    // 2. 清理 Worktree
    // 3. 清理团队目录
```

注意第 1 步：**有队员还在活跃就拒绝清理**。这是防止「活没干完就把台子拆了」。

清理完**不留痕迹**——就像这个团队从来没存在过。唯一留下的是**合并进主分支的代码和 Git 历史**。

## 队员空闲与续写：为什么队员不是一次性的

上面的生命周期是一条直线：建团队 → 干活 → 合并 → 清理。

但真实工作不总是一条直线。队员完成任务后，Lead 可能发现**还需要补一个测试**；或者用户临时改了需求。

这时候重新 spawn 一个新队员太浪费了——新队员没有之前的上下文，得从头把情况了解一遍。

所以设计了一套**空闲与续写**机制。

### 停下来：两步通知 Lead

队员的 `runToCompletion` 结束时（也就是 LLM 返回纯文本、不再调用任何工具的时候），意味着这个队员认为自己的活干完了。系统通过两步通知 Lead：

```
function onTeammateStop(team, teammateName):
    setMemberActive(team.name, teammateName, isActive=false)   // 1. 标记空闲
    mailbox.write(team.leadAgentID, idleNotification)          // 2. 通知 Lead
```

Lead 只要看一眼团队配置，就知道哪些队员停下来了——**以便判断该追加任务，还是该启动收敛**。

### 再唤醒：从磁盘上的对话记录里把它捞回来

更关键的是续写。队员空闲后、**甚至被强制终止后**，Lead 都可以通过 `SendMessage` 给它发新指令。

系统会自动检测目标队员的状态：**如果已停止，就从磁盘上的对话记录把它恢复起来，带着完整的历史上下文继续工作。**

```
// alice 已经完成任务停下来了，Lead 发现还需要一个集成测试
SendMessage(to="alice", message="还需要一个集成测试，请在 test/ 目录下补充端到端测试")
// → 系统检测到 alice 已停止 → 从磁盘 transcript 恢复
// → alice 带着之前的完整上下文继续工作
```

### 这一条划出了 SubAgent 和队员的分界线

| | 干完活之后 |
|---|---|
| 普通 SubAgent | **上下文丢弃**。下次有事重新派、重新讲一遍背景 |
| Team 队员 | **上下文持久化到磁盘**，随时可以唤醒续写 |

所以队员的生命周期是灵活的：**可以暂停、恢复、重新指派**。它们是**持续性的工作者**，而不是一次性的人力。

用管理的话说：SubAgent 是外包合同（交付即结束），队员是员工（离职了也能叫回来接着干）。

> ACode 的现成落点：ACode 已经有**项目级会话池**（`.acode/sessions/` 下的 JSONL 逐条追加写入，`--resume` / `/resume` 恢复并续写同一文件），也有 `session` 包的整套读写组件。队员的「磁盘 transcript + 恢复续写」需要的持久化能力，这里已经有一份同构的实现可以参考。

## 任务分解策略：Lead 的手艺

Lead 怎么把用户目标拆成任务，**直接决定团队的执行效率**。

两个方向都会翻车：

- **拆得太粗** → 单个任务工作量太大，并行度上不去
- **拆得太细** → 任务之间依赖太多，队员大部分时间在等

四条实用原则：

**一、按文件边界分任务。**

两个任务如果改同一个文件，合并时大概率冲突。尽量让每个任务操作**不同的文件集**。

实在避不开同一个文件怎么办？**把改同一个文件的那些任务放到有依赖关系的链上，强制它们串行。** 宁可牺牲并行度，也不要在合并阶段制造冲突。

**二、控制每个队员的任务数。**

经验值：**每个队员排 2～4 个任务**。

再少，队员很快做完就空闲了，养着一堆闲人。再多，任务列表看起来吓人，**LLM 选任务时反而容易纠结**——选项太多的决策质量会下降，这一点对模型和对人都成立。

**三、依赖关系要明确。**

如果任务 C 依赖任务 A 的输出，**用 `addBlockedBy` 建立系统级依赖，同时在任务描述里写清楚原因**：

> 需要在 T1 完成后再开始，因为要用到抽取后的接口

**不要指望队员「应该知道」要先做 A 再做 C。** LLM 不一定能推断出隐含的顺序——把知识写在它看得见的地方。

**四、留一个验证任务。**

所有修改任务完成后，加一个**验证任务**：编译、跑测试、检查 lint。

这个任务**依赖所有修改任务**，确保它只在所有修改都完成后才执行。

前面提过，ACode 现有代码里没有 Task 相关的工具——这套任务管理能力本章要新建。上一章（`ch12`）已经明确把 `TaskManager` 和后台任务基础设施「留给下一阶段」，这里正好接上。

## 冲突预防：三层防线

多个队员并行改代码，**合并冲突是最大的风险**。三层预防，从物理到智能：

**第一层：Worktree 隔离。** 每个队员在自己的 Worktree 里工作，工作过程中**根本碰不到彼此**。这是最硬的一层——不靠自觉，靠文件系统。

**第二层：任务拆分。** Lead 分解任务时**按文件边界切**，让不同队员改不同文件，让冲突在**源头**就不产生。

**第三层：LLM 驱动的智能合并。** 真撞上了，收敛阶段 Lead 用 `Bash` 执行 `git merge`，遇到冲突用 `ReadFile` 检查冲突标记，自己判断怎么解决。

**Lead 像人类开发者一样操作 git，只是更快。** 大部分机械冲突自己能搞定，涉及逻辑矛盾的交回用户。

三层的关系是：**能物理隔离就物理隔离，隔离不了就在源头避开，避不开就用理解力兜底。**

## Coordinator Mode：让 Lead 专注调度

机制讲完了，但有个问题还挂着：**Lead 派完队员之后，自己手里还留着全套工具。**

它可以一边协调队员，一边自己用 `ReadFile` 看代码、用 `Bash` 跑命令，甚至自己改文件——这就是开头场景三说的问题。

小团队没事。但任务复杂、队员一多，**Lead 一心二用会出两个具体问题**：

1. 它自己改代码会占用**主仓库的 worktree**，和队员的修改直接冲突
2. 它的上下文窗口已经被任务列表、队员状态、消息记录占掉不少，**再往里塞代码内容只会互相干扰**

Coordinator Mode 就是为这个场景设计的。

要强调一个定位：它是**独立于 Agent Team 的一个可选能力**。团队可以不开协调模式；协调模式也只是一道**纪律约束**——进入后，Lead 被剥夺所有代码操作工具，只能专注调度。

### 激活条件：两把锁都要开

```
function isCoordinatorMode() -> bool:
    if not feature('COORDINATOR_MODE'): return false
    return isEnvTruthy(process.env.ACODE_COORDINATOR_MODE)
```

两把锁的意图不同：

- **feature flag**：让**开发者**可以按需开关这个能力
- **环境变量**：让**用户**显式 opt-in

第二把锁的意义在于——**避免在用户不知情的情况下改变 Lead 的行为模式**。一个会突然发现自己不能改代码的 Agent，是很吓人的。

### 工具集收窄

进入 Coordinator Mode 后，Lead 的工具集被收窄到两组：

```
COORDINATOR_MODE_ALLOWED_TOOLS = [
    Agent, SendMessage,                                   // 派人和通信
    TaskCreate, TaskGet, TaskList, TaskUpdate,            // 任务管理
    TeamCreate, TeamDelete,                               // 团队管理
    ReadFile, Glob, Grep, Bash,                           // 读类 + shell
]
```

注意**没有** `WriteFile` / `EditFile`——**Lead 在协调模式下不直接改代码**。

但读类和 `Bash` 都留着，各有各的理由：

- **`Bash` 必须留**：收敛阶段 Lead 要跑 `git merge`，没它合不了分支
- **`ReadFile` / `Glob` / `Grep` 必须留**：Synthesis 阶段 Lead 得消化队员的研究结果、写实施规格，没读类工具就没法工作

可以这样理解 Coordinator Mode：

> **剥夺 Lead 自己动手写代码的权力，但保留它读代码、跑 git、协调队员的能力。**

用一个我们熟悉的类比：这就是**技术负责人不再亲自写业务代码**——但他还得看代码、看得懂设计方案、能拍板。

### 四阶段工作流

Coordinator Mode 不只是收窄工具集，还会注入一套 coordinator 系统提示词，把大部分任务规范成四个阶段：

| 阶段 | 执行者 | 目的 |
|---|---|---|
| **Research** | 队员，可并行 | 调查代码库、定位文件、理解问题 |
| **Synthesis** | **Lead 自己** | 阅读调查结果、理解问题、**撰写实施规格** |
| **Implementation** | 队员 | 按规格修改代码、提交 |
| **Verification** | 队员 | 测试改动是否正确 |

**四个阶段里最关键的是第二个：Synthesis。**

这是 Lead 作为 coordinator **最核心的职责**：理解队员的研究结果，然后写出**具体的实施规格**交给下一批队员执行。

系统提示词明确要求——**Lead 不能把「理解」这个能力委托出去**：

```
// 反面模式：把理解委托给队员
Agent(prompt="基于你的调研结果，修复认证 bug")

// 正确模式：Lead 自己理解后给出具体指令
Agent(prompt="修复 src/auth/validate.java:42 的空指针。
    Session 类型的 user 字段在 session 过期但 token 仍在缓存时为 undefined。
    在访问 user.id 之前加空值检查，如果为 null，返回 401 'Session expired'。
    提交并报告 commit hash。")
```

看这两个例子的差别：

- 反面模式里，Lead 只是**把任务转手**了——「基于你的调研结果」意味着**理解的责任被推回给了队员**，队员既要知道问题是什么、又要知道怎么修。
- 正确模式里，Lead **自己完成了理解和定位**，给队员的是一份**可以直接执行的规格**：改哪个文件哪一行、原因是什么、怎么改、验收标准是什么。

这背后的判断是：**Research 可以并行外包，理解不能。** 如果 Lead 把理解也委托出去，那它就不再是协调者，只是一个消息转发器——那它和上一章的星型拓扑有什么区别？

**协调者的价值，恰恰在于它是唯一一个能看到全局的人。**

### 结果投递与续写循环

队员干完活，Lead 怎么知道结果？

上一章讲后台任务时提到过 `<task-notification>` 通知机制，当时只讲了原理。这里补上它的完整格式——在 coordinator 工作流里会频繁看到：

```
<task-notification>
  <task-id>{agentId}</task-id>
  <status>completed | failed | killed</status>
  <summary>Agent "Investigate auth bug" completed</summary>
  <result>{队员的最终文本回复}</result>
  <usage>
    <total_tokens>N</total_tokens>
    <tool_uses>N</tool_uses>
    <duration_ms>N</duration_ms>
  </usage>
</task-notification>
```

Lead 看到通知后，可以用 `SendMessage(to="{agentId}", message="...")` **续写**这个队员，让它继续做后续工作。

于是 coordinator 的核心工作模式就是一个循环：

```
spawn → 收结果（task-notification）→ Synthesis → 续写（SendMessage）→ spawn …
```

**注意这个循环里没有「重新建一个队员」，只有「叫醒上一个队员」。** 这就是前面「空闲与续写」存在的意义——它让这个循环变得便宜。

## 教材的 Java 参考实现：一个精简版

教材除了理论，还给了一份 Java 参考实现（4 个文件，约 500 行），值得单独看——**因为 ACode 也是 Java，这份参考在工程取舍上很有参考价值**。

| 文件 | 行数 | 职责 |
|---|---|---|
| `TeamManager.java` | ~149 | `TeamManager` / `Team` / `Member` 三层嵌套类，成员生命周期 |
| `FileMailBox.java` | ~133 | 基于文件的收件箱，JSON 存储 + 文件锁 + 乐观重试 |
| `Coordinator.java` | ~37 | 协调模式的工具白名单 |
| `TeamTools.java` | ~183 | `SendMessage` / `TeamCreate` / `TeamDelete` 三个工具的完整实现 |

它比理论篇简单不少，几个取舍值得注意：

| 方面 | 参考实现的做法 |
|---|---|
| 后端 | `TeamMode` 只有 `IN_PROCESS` 和 `TMUX` 两个值，没有 iTerm2 |
| 后端检测 | 只看两件事：`TMUX` 环境变量、`which tmux`；都不满足**静默退化为 in-process** |
| 团队持久化 | **纯内存**。`Team` 没有 `save` / `load`，程序重启团队信息就没了 |
| 成员执行 | 每个 `Member` 持有独立的 `Agent` + `ConversationManager`，**虚拟线程**执行 |
| 成员停止 | 统一 `Thread.interrupt()`，不区分后端类型分别处理 |
| 消息查找 | `SendMessage` **全局遍历所有团队**找收件人，**没有名称注册表** |
| 锁过期 | 超过 10 秒的锁文件视为过期，强制删除 |
| 消息语义 | **读完标记**（`markAllRead`），消息不删除，可追溯 |
| 协调模式 | 只是一个**不可变白名单集合**，只回答「这个工具允许协调者用吗」，系统提示由上层管理 |
| 命名冲突 | 团队名撞了就加数字后缀（`team-2`），**检查内存 map 而不是磁盘目录** |

值得留意的是：这份参考实现**有意识地砍掉了很多东西**——没有名称注册表（全局遍历更简单）、没有磁盘持久化（团队生命周期通常和会话绑定）、iTerm2 后端直接不做。

**这说明理论篇讲的是一套完整设计，而真正落地时可以按需裁剪。** 哪些是骨头（文件邮箱、协调工具、白名单隔离），哪些是肉（名称注册表、多后端、持久化），心里要分得清。

## 设计哲学

**协调机制是工具，不是基础设施。**

这一章从头到尾在做同一件事：把协调能力做成**工具**发给每个队员，而不是做成**调度器**塞进框架。

回看那几个设计选择，全都是这一条推出来的：

- 不写「谁先说话谁后说话」的调度逻辑，而是给每个队员 `TaskList` 让它自己看
- 不做「Lead 强制分配任务」，而是让队员从列表里**自己认领**
- 不引入消息队列、不引入 RPC，只用**文件邮箱 + 共享任务列表**把队员粘起来
- 协调模式不做成复杂的权限引擎，只是一个**不可变的白名单集合**

代价和收益都说清楚：

- **代价**：行为不像状态机那么可预测。你不会拿到一张确定的执行图。
- **收益**：想新增一种协作方式，**只需要加一个工具**。「调度器不存在，也就不需要改」。

上一章的设计哲学是「**能力边界优于行为约束**」——不给工具，就是最强的约束。这一章的「**协作能力是工具**」是同一条血脉的另一面：**给工具，就是最强的赋能。**

**把 Agent 当成有判断力的协作者，而不是流水线上的某个工位。** 这是整章的设计前提。如果你不认同这个前提，那这一章的所有取舍看起来都会是「偷懒」；如果你认同，那没有调度器就不是缺失，而是**刻意留白**。

## 边界

- **不做跨机器的分布式 Team。** 队员都在同一台机器上。跨机器涉及服务发现、网络分区、认证，是另一个量级的问题，收益在这一章也不明显。

- **不做队员之间的实时流式通信。** 通信走「文件邮箱 + 轮询」，本质上异步。队员看到别人的消息最多延迟一个轮询间隔。要做到 token 级的实时互通，就得引入长连接或消息队列——那正是「基础设施」路线，和本章的设计哲学相悖。

- **依赖 Worktree 章（`docs/ch13/`，设计稿已出、代码待落地）。** 队员的独立工作目录、收敛阶段的合并、冲突预防的第一层，全部建立在它之上。**本章只消费、不实现。** 在它落地之前，队员只能共享主 Agent 的工作目录——此时并行修改的冲突风险要靠任务拆分来兜，兜不住的部分会显式暴露出来，而不是假装安全。

- **不实现 tmux / iTerm2 多 pane 后端（本章先做 in-process）。** 教材设计了三种后端，其中 pane 后端的价值是**进程级隔离 + 生命周期不依赖 Lead**。ACode 的终端 UI 基于 JLine，拉起独立的 tmux pane 需要额外管理子进程、CLI 启动参数、pane 生命周期，工程量不小。**先在 in-process 后端把协调机制（任务列表 + 邮箱 + 团队生命周期）做扎实**——这部分逻辑三种后端完全一致——pane 后端留作后续增量。这不是砍掉，是分批：**底座不变，只换执行位置。**

- **不做团队的跨会话持久化。** 教材的 Java 参考实现是纯内存的（团队生命周期通常和会话绑定）。ACode 有现成的会话池技术，但「重启后恢复一个还活着的团队」涉及队员状态、邮箱内容、Worktree 归属的整体恢复，本章不做。**队员的上下文持久化（续写用）和团队本身的持久化是两件事**，前者要做，后者不做。

- **不做团队规模的自动治理。** 队员不能 spawn 队员（防扩张）、Coordinator Mode 收窄工具集，这两条是**约束**。但「团队最多几个人」「任务太多怎么自动再平衡」这类治理策略本章不做，交给 Lead 的 LLM 判断。

- **不做 Plan 审批的可视化。** `planModeRequired` 和 `plan_approval_response` 是**协议层**的能力。通过审批时在终端里怎么展示、用户体验怎么设计，不在本章范围。

- **不硬化任务分解策略。** 上一节那四条原则是**给 Lead 提示词的建议**，不是系统强制。硬编码分解策略等于把调度器又请回来了。
