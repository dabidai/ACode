# Skill 系统 —— 可复用的技能包

> 本文保留最初的需求讨论与示例。2026-09-26 已对照 ACode 当前代码核查；实施口径以同目录 `spec.md`、`tasks.md`、`checklist.md` 为准。特别注意：`LoadSkill` 的独立正文须在同批全部 `tool_result` 之后入历史；工具范围也须在实际执行入口校验；多个 Skill 的范围、热加载版本及 jar 资源枚举见验收清单。文中“全绿报告覆盖率”以项目已有报告为前提。

> 把「反复手打的一段 prompt + 一组相关工具」变成可编辑、可分发、按需加载的 Markdown 资产

## 为什么需要它

用了 ACode 一段时间之后，你大概会养成一些习惯。

每次提交代码，你都会打一段类似的话：

```
请分析当前 git diff，生成一个规范的 commit message。格式要求：
type(scope): description，type 从 feat/fix/docs/refactor/test 中选。
然后用 git add 和 git commit 执行提交。不要 add 敏感文件。
```

每次做代码审查，你又会打：

```
请审查当前 git diff 的代码变更。重点关注：
1. 逻辑错误和边界条件
2. 安全漏洞
3. 性能问题
4. 代码风格一致性
按严重程度分级报告。
```

每次跑测试，你还要打一段更长的话，告诉 Agent 怎么检测项目类型、怎么分析失败原因、怎么区分代码 bug 和测试本身的问题。

这些 prompt 每次打都一样（或者几乎一样），但又必须打。因为不打的话，Agent 不知道你要什么格式、什么标准。

**还有第二个问题，比第一个更隐蔽。**

回头看 ACode 现在的工具列表：`ReadFile`、`WriteFile`、`EditFile`、`Bash`、`Grep`、`Glob`，六个。接上 MCP 之后可能是十五个、二十五个。工具越多，模型的选择准确率越低。常见的翻车场景：

- 该用 `Grep` 搜索时，它选了 `Bash` 的 `grep` 命令——功能差不多，但权限控制被绕过去了
- 二十个工具摆在面前，它分不清什么场景该用 `Glob`、什么场景该用 `Grep`，挑了个相近但错的
- 该先 `git diff` 看变更再 `git add` 暂存，顺序搞反了，结果完全不对

这和人一样：三个选项能快速决策，三十个选项就开始纠结了。

你可能想到了上一章的 Slash Command，特别是 `prompt` 类型。上一章实现的 `/review` 就是这种命令，把一段写死在 Handler 里的代码审查 prompt 转发给 Agent。同样的思路也能搞 `/commit`：注册一个 `prompt` 类型的命令，Handler 里硬编码 commit 流程的 prompt。

但问题是，**Handler 是源代码**。修改一个 prompt 就得重新编译，而且用户没法添加自己的命令。你总不能因为想调整 commit message 的格式，就去改源码然后重新构建一次。

所以我们面对的是两个问题：

- 可复用的 AI 操作需要变成**独立的、可编辑的、不需要编译的**东西
- 需要一种机制，让模型在执行特定任务时**只看到相关的工具和指令**，提高调用准确率

Skill 系统同时解决这两个。

## Skill 是什么：写给 Agent 的 SOP

在聊技术实现之前，先理解它的本质。

你在公司里大概见过 SOP（Standard Operating Procedure），就是「标准操作流程」。新人入职，给他一份 SOP：「当你要部署时，按照 1、2、3 步骤来」。SOP 是写给人看的，人按照流程去执行。

**Skill 就是写给 Agent 的 SOP。** 区别只在于：SOP 给人看、人来执行；Skill 给 Agent 看、Agent 来执行。

但有一点很关键：**人类可以「领会精神」，Agent 不行，它只会「照字面做」。**

你写「注意安全」，人知道要检查 SQL 注入和 XSS。你写「注意安全」给 Agent，它可能只会在回复里加一句「已注意安全问题」就完事了。

所以 Skill 里的指令需要比人类 SOP **更精确、更具体**。这一点在写内置 Skill 时会反复体现。

### 和 Slash Command 的关系

上一章把 Slash Command 拆成了三类，先把这条线接上：

| 类型 | 做什么 | 代表 | 耗 token |
|---|---|---|---|
| `local` | 纯本地操作，结果以系统消息显示 | `/help`、`/status` | 否 |
| `local-ui` | 本地执行，但会改 UI 状态或会话状态 | `/clear`、`/plan`、`/do` | 否 |
| `prompt` | 把一段预设 prompt 转发给 Agent | `/review` | 是 |

Skill 的思路**接续 `prompt` 类命令这条线**。两者的核心都是「把一段固定 prompt 模板交给 Agent 执行」，让用户少打几个字，也让 prompt 经过精心设计后质量更稳定。

但 `prompt` 类型还留着几个痛点没解决：

- prompt 硬编码在源码里，改一个字就要重新编译
- 只有开发者能加新命令
- 命令执行时拿到的工具范围跟普通对话一模一样，**没有工具级隔离**
- 它没法捎带任何资源——prompt 只是一段孤零零的字符串，带不了专属的工具实现、参考文档或脚本

Skill 就是来把这些一并补齐的：把 prompt 从源码搬进独立的 Markdown 文件，任何用户都能新增和修改；再加上工具白名单、执行模式、参数替换，把一个「带快捷方式的 prompt」演化成一套完整、自包含、可分发的任务系统。

### 那该怎么选？

判断顺序是这样的：

```
纯执行、不需要 AI 判断的 ─────────────→ local / local-ui 命令
需要 AI 判断 ─┬─ 复杂度低、不需用户自定义、不需工具隔离 → prompt 类命令
              └─ 超过这条线 ──────────────────────→ 升级成 Skill
```

`/clear` 是典型的 `local` 命令，清屏就是清屏。`/commit` 是典型的 Skill——分析 diff、生成 message、选择要 add 的文件都需要 AI 判断，而且每个团队的 commit 规范不一样，必须让用户能直接编辑配置。

打个比方：`local` 和 `local-ui` 命令像**电灯开关**，按下去灯就亮，确定性百分之百。Skill 像**给一个实习生的任务清单**，他会按你的指示去做，但具体执行过程中有自己的判断空间。`prompt` 类命令介于两者之间，相当于把任务清单贴在了开关旁边的告示板上，能用，但灵活度有限。

## 定义文件：Markdown + YAML

Skill 的定义格式是 Markdown。为什么是它？因为它同时满足三个需求：**人类可以直接阅读**，**系统可以通过 YAML frontmatter 解析结构化数据**，**LLM 可以直接理解 body 里的指令**。

一个完整的 Skill 文件长这样：

```markdown
---
name: commit
description: 分析 git diff 并生成规范的 commit
allowedTools:
  - Bash
  - ReadFile
  - Grep
mode: inline
---

# 任务

你需要帮用户创建一个 git commit。

## 步骤

1. 运行 `git status` 查看当前变更状态
2. 运行 `git diff` 和 `git diff --staged` 查看具体变更内容
3. 分析变更，确定 commit 类型和范围：
   - feat: 新功能
   - fix: 修复 bug
   - docs: 文档变更
   - refactor: 重构
   - test: 测试
   - chore: 构建/工具变更
4. 生成 commit message，格式：`type(scope): description`
5. 用 `git add` 添加相关文件（不要添加 .env、credentials 等敏感文件）
6. 执行 `git commit -m "生成的 message"`
7. 如果用户提供了额外说明，纳入 commit message

## 注意事项

- 不要用 `git add -A`，逐个文件添加
- commit message 用英文
- description 不超过 72 个字符
- 如果变更太多，建议用户拆分成多个 commit

$ARGUMENTS
```

上半部分是 YAML frontmatter（两个 `---` 之间），定义元信息。下半部分是 **prompt body**，就是实际发送给 LLM 的指令。

这意味着什么？你要调整 commit message 的格式规范，打开这个 `.md` 文件改几行文字就行了，不用碰源代码，不用重新编译。你想加一个新 Skill，创建一个 `.md` 文件就行了。

### frontmatter 里的每个字段

YAML frontmatter 是 Skill 的「身份证」。逐个看：

**`name`（必填）** —— Skill 的唯一标识符，**同时也是调用它的命令名**。`name: commit` 意味着用户可以通过 `/commit` 调用它。命名规范是小写字母、数字和连字符。注意不能和内置命令冲突——你不能定义一个 `name: help` 的 Skill，因为 `/help` 已经被 ch09 的内置命令占了。**这个冲突在加载时就要检测出来。**

**`description`（必填）** —— 一句话描述 Skill 的功能。它有两个用途：出现在 `/help` 列表里，以及**给模型看，用于判断该不该加载这个 Skill**。所以它得写清楚「这个 Skill 能做什么」和「什么时候该用它」。

> 说明：`description` 的写法直接决定模型能不能挑对 Skill，是整套机制里最容易被低估的一个字段。后面讲「两阶段加载」时会看到，**第一阶段的清单里只有 `name` 和 `description` 两项**，模型全靠这两行字做决定。

**`allowedTools`（推荐填）** —— 限制 Skill 执行期间可以使用的工具。为什么需要它，后面单独讲。

**`model`（可选）** —— 指定 Skill 使用的模型。有些任务简单（生成 commit message），可以用便宜一点的模型；有些任务复杂（代码审查），值得用最强的。不指定就用默认模型。

**`mode`（可选）** —— 控制执行模式：`inline`（默认）或 `fork`。这个区别很重要，后面专门讲。

**`context`（可选）** —— 只在 `fork` 模式下生效，决定把多少主对话的上下文带进 fork 会话：

| 值 | 含义 |
|---|---|
| `full` | 把主对话压成一段摘要带进去（默认） |
| `recent` | 只带最近 5 条消息 |
| `none` | 完全不带，彻底隔离 |

`inline` 模式本身就共享对话历史，这个字段会被忽略。

> 说明：还有几个字段是**业界 Skill 格式的通用字段**，但 ACode 本章先不做，了解一下就好：`argument-hint`（给 `/name` 提示参数该写什么）、`disable-model-invocation`（禁止模型自动触发，只能用户手动调）、`user-invocable`（是否给用户 `/name` 入口）。这些主要是「触发控制」层面的开关，不影响本章要讲的核心机制。

## 三个地方找 Skill

Skill 文件可以放在三个位置，按优先级从高到低：

```
1. 项目级：{项目根}/.acode/skills/
2. 用户级：~/.acode/skills/
3. 内置级：编译进 jar 的 Skill
```

这个设计你应该不陌生——ACode 的配置体系（`ConfigLoader` 三级链）和项目指令加载（`ACODE.md` 三层）都是这个思路：**离使用场景越近，越有话语权**。Skill 沿用同一条约定。

也跟 Git 的 `.gitconfig` 一样：项目级配置覆盖全局配置。

### 查找语义：覆盖，不是叠加

实现上维护一个 `seen` 集合，**按优先级从高到低扫描**：每读到一个 Skill，先看名字在不在集合里；不在就收下并记录，已经在了就跳过。这样高优先级目录里的同名 Skill 自然就把低优先级版本盖住了。

**解析失败的文件记一条日志、跳过即可**，不要让单个坏文件中断整个加载流程。

> 说明：这里的「找到一个就停」和 Hook 的查找语义**正好相反**。Hook 配置是**追加合并**的——`docs/ch11` 里讲过，项目规定「所有写文件都要格式化」，你个人再加一条「写完 Python 顺便跑类型检查」，两条同时生效。Skill 不行：`commit` 只能有一个版本，必须有个明确的胜负。为什么不一样？因为 Hook 是**规则**，多一条规则不冲突；Skill 是**身份**，同一时刻只能有一套 SOP 说了算。

这种覆盖策略带来几件很实用的事情：

- **项目可以定义项目特有的 Skill。** 你的项目有自己的部署流程，写一个 `deploy.md` 放在 `.acode/skills/` 下面就行
- **用户可以定义个人通用的 Skill。** 你喜欢 commit message 用中文？写一个自己版本的 `commit.md` 放在 `~/.acode/skills/`，它会覆盖内置的英文版
- **项目级 Skill 可以提交到版本控制，整个团队共享。** 团队的最佳实践从口头传授变成一个个可执行的 Skill 文件，新人 clone 仓库就自动加载了

内置 Skill 则通过**资源嵌入**编译进 jar——ACode 是 Maven 项目，把内置 Skill 的 `.md` 放在 `src/main/resources/skills/` 下，通过 classpath 资源读取，不依赖外部文件。

## 两阶段加载：本章的核心

到这里都还是「一个文件格式」。真正让 Skill 系统立住的是这一节。

### 问题：31 个 Skill 不能一次全塞

假设你的 Skill 库慢慢长大，项目级 3 个、用户级 5 个、内置 3 个。如果启动时把所有 Skill 的**完整正文**都塞进上下文，会发生什么？

- 上下文被瞬间吃掉一大块
- 更要命的是**注意力被稀释**——模型面前摆着 11 份互相无关的 SOP，它得从中挑出该看哪一份
- 而你这一轮可能只想提交个代码，另外 10 份 SOP 是完全无关的噪音

这正是我们开头说的第二个痛点的放大版：不是工具太多，是**指令太多**。

### 解法：拆成两个阶段

关键思路是把加载拆成两段。

**第一阶段：轻量注册。** ACode 启动时只加载每个 Skill 的 **frontmatter**（`name` + `description`），不加载完整正文。这些轻量信息拼成一段清单，注入到 system prompt 里：

```
你可以使用以下 Skill：

- commit：分析 git diff 并生成规范的 commit。
- test：运行测试并分析结果，区分代码 bug 和测试本身的问题。

如果用户的请求匹配某个 Skill，请调用 LoadSkill 工具加载它。
```

模型平时只看得到这份清单。开销是恒定的——**和 Skill 的数量成正比，和正文大小无关**。三十个 Skill 也只是几百个 token 的清单。

**第二阶段：按需加载。** 当模型判断用户意图匹配某个 Skill 时，它调用 `LoadSkill` 工具。这个工具做三件事：

1. 把 SKILL.md 的完整正文**加载进当前对话**
2. 把该 Skill 的工具白名单挂上
3. 返回一句简短的确认信息

这就是**渐进式披露**（progressive disclosure）：模型先知道「有什么能力可用」，确定要用之后才去拿「具体怎么做」。既省上下文，也把选择压力降到最低。

### 两条触发路径

用户可以显式调用，模型也可以自主识别：

| 触发方式 | 路径 | 谁做判断 |
|---|---|---|
| 用户打 `/commit` | 命令注册中心 → Skill 执行器 → 直接加载正文 | 用户显式指定 |
| 用户说「帮我提交一下」 | 模型识别意图 → **调用 `LoadSkill` 工具** | 模型自己 |

两条路的终点是同一个动作（加载并激活 Skill），之后执行流程完全一样。这也是为什么 Skill 会自动注册成 Slash Command——**让 `prompt` 类命令那条线自然延伸过来**。

> 说明：注册这个动作本身比较简单——遍历所有 Skill，给每个在 ch09 的命令注册中心建一个 `PROMPT` 类型命令，命令名取 `name`，描述沿用 `description` 并在末尾加一个 `[skill]` 标记，Handler 指向 Skill 执行器（而不是像 `/review` 那样硬编码 prompt 字符串）。ch09 特意把注册中心改成读写锁保护，**就是为这里的运行期动态注册铺的路**。注册完成后，Skill 和内置命令在用户看来没有区别：都是 `/xxx` 调用，都在 `/help` 里，都支持 Tab 补全——唯一的区别是标注了 `[skill]`。
>
> 另外有一个容易忽略的坑：**热加载**。每次执行 Skill 时都重新解析文件，这样你改了 `commit.md`，下次输入 `/commit` 就用新的 prompt，不用重启 ACode。解析失败时回退到缓存版本，避免一处坏文件把整个命令搞挂。

> 配套的还有一个管理命令 `/skill`，用来查看和维护 Skill：`/skill list` 列出所有已加载的 Skill 及来源，`/skill info <name>` 显示指定 Skill 的完整 frontmatter 和文件路径，`/skill reload` 重新扫描并加载所有 Skill 文件。开发和调试自定义 Skill 时会经常用到 `reload`。

### 正文怎么进上下文：追加成一条 user 消息

这是本章最需要想清楚的一个设计点，值得单独讲。

`LoadSkill` 拿到 SKILL.md 的正文之后，**它是怎么进入对话的**？有三种可能的做法，各有代价：

**做法一：作为 `tool_result` 返回。**
最直觉的做法——工具调用返回内容，正文自然进对话。但它有个问题：**tool_result 是给模型看「你那个工具调用的结果」的**，把一整份 SOP 塞进去语义不对；而且正文从此成为历史里的一条工具结果，会随着对话增长被越推越远。

**做法二：每轮重新注入。**
每轮请求都重新把已激活的 SOP 拼进去，保证它永远在显眼位置。代价是**每轮都要重复付这份 token**，而且一旦有新的 Skill 被激活，请求前缀就变了——对 prompt cache 很不友好。

**做法三：追加成一条独立的 user 消息，进历史，只做一次。**
这是 ACode 采用的方案。

具体流程是：

```
模型调用 LoadSkill("commit")
      ↓
① 回一条占位的 tool_result（内容只是一句确认）
      ↓
② 把 SKILL.md 正文作为一条独立的 user 消息，追加到消息列表末尾
      ↓
③ 这条消息留在对话历史里，后续轮次自然都看得到
```

这么做的好处：

- **只付一次 token。** 正文进历史后就成为稳定前缀的一部分，后续轮次是 cache 命中，不像「每轮重注」那样反复计费
- **`/clear` 自动清理。** 正文在历史里，清空历史就清掉了它，不需要额外的「已激活 Skill」清理逻辑
- **多条 Skill 共存是天然的。** A 执行中又加载 B，两条 user 消息都在历史里，两份 SOP 同时在场

代价是它会随对话增长被推得越来越靠上，注意力会衰减。但这里有个关键缓冲：**第一阶段的那份清单在 system prompt 里，压缩和清空都不碰它**。所以就算某份 SOP 被推远了、甚至被压缩掉了，模型随时可以照着清单**重新加载一次**。

> 说明：**关于那个「占位的 tool_result」**——它不是可选的，是必须的。ACode 的 `Conversation.sanitize()` 在请求出口会**剔除无配对的 tool_use 块**（这是为了兜住脏会话恢复和中断留下的悬空工具调用）。如果模型调了 `LoadSkill` 却不回 `tool_result`，这条 tool_use 会被清洗掉，模型会以为自己压根没调过这个工具。所以必须回一条占位结果，真正的正文走另一条 user 消息。

### 清单里为什么只放两样东西

回到第一阶段的清单。它里面**只有 `name` 和 `description`**，不放正文、也不放文件路径。

不放正文容易理解（那就不是渐进式披露了）。**不放路径**这一点值得展开：

如果清单里给了文件路径，模型很容易想「我直接 `ReadFile` 那个文件不就行了」，然后绕过 `LoadSkill` 去读。后果是三重的：

1. 正文落进 `tool_result` 变成历史的一部分，随对话被推远——正是这种做法要避免的
2. **该 Skill 的工具白名单不会生效**——工具隔离失效
3. 该 Skill 附带的资源（后面讲的 `references/`）不会被正确关联

所以清单里只给「有什么」和「干什么用」，不给「在哪儿怎么读」。**读取方式由框架统一承担**，这样才有机会做白名单和资源关联。

> 说明：这确实是一个设计选择，不是唯一答案。有的实现（比如 OpenAI 的 Codex CLI）走的是另一条路——清单里给位置，明确指示模型「决定要用之后，先完整读取它的 SKILL.md 再动手」，由模型自己用文件读取工具去读。**代价就是上面第 1、2 条**：正文进的是工具结果历史，且没有白名单机制。两条路都能跑通，ACode 选前者，因为本章要讲的白名单和资源关联都依赖「框架知道你在用哪个 Skill」。

### 清单放在哪：system prompt

清单的注入位置也有个取舍。

ACode 把它放进 **system prompt**（通过 `PromptBuilder` 加一节）。好处是它落在 **prompt cache 的稳定前缀区**——Skill 清单反正不常变，缓存收益很大。

另一种做法是**每轮把它当作 system-reminder 塞在 user 消息层**。好处是 `/skill reload` 之后下一轮立刻见效，但每轮都要多带一段 token。

两种都跑得通，权衡的是 **cache 命中**和 **reload 即时性**。ACode 选前者，因为清单本身很少变，而 system prompt 的位置让它可以一直躺在缓存里。至于 reload 的即时性——重新扫描后重建一次 system prompt 就够了，不值得为此每轮多付 token。

## 目录型 Skill：带资源的技能包

前面一直把 Skill 画成「一个 Markdown 文件」。但渐进式披露还有第三层没用上。

一个 commit Skill 只需要一段 SOP。但如果我们要写一个「模拟后端技术面试」的 Skill 呢？它需要一份**出题指南**（长文档）、一个**解析简历的脚本**（确定性的活儿不适合让模型现写）。这些塞不进一个 `.md`。

所以 Skill 从单文件演化成了一个**目录**：

```
.acode/skills/backend-interview/
├── SKILL.md              # 入口：frontmatter + SOP 流程
├── scripts/              # 可执行代码
│   └── parse_resume.py
├── references/           # 需要时才读进上下文的文档
│   └── interview-guide.md
└── assets/               # 不进上下文，用于产出
    └── report-template.md
```

`SKILL.md` 是入口，角色和单文件 Skill 完全一致。三类资源各有各的定位：

| 目录 | 什么时候用 | 进上下文吗 |
|---|---|---|
| `scripts/` | 操作用是确定的（校验、格式化、解析），或者同一段代码会被反复重写 | **不一定**——可以直接执行，不读进上下文 |
| `references/` | 文档、API 参考、领域知识、详细流程 | **按需**——模型判断需要时才读 |
| `assets/` | 模板、图标、字体等**用于产出**的文件 | **不进上下文**——是被复制/修改到结果里的 |

这就是渐进式披露的**第三层**：

```
第一层  name + description   →  永远在 system prompt 里（~100 词/Skill）
第二层  SKILL.md 正文        →  Skill 激活时加载（建议 1500~2000 词）
第三层  目录里的资源          →  模型按需取用（上不封顶）
```

第三层「上不封顶」是有前提的：**脚本可以直接执行而不读进上下文**。一个 2000 行的解析脚本，模型不需要看懂它，只需要会调它。

### 脚本怎么执行：用 Bash 跑，不包装成工具

这一点上有个容易走偏的方向：**不要**把脚本注册成一个新工具。

ACode 已经有 `Bash` 工具，脚本的执行就是普通命令。SOP 里写清楚怎么调：

```
## 步骤

1. 运行 `python scripts/parse_resume.py <简历路径>` 获取结构化的简历信息
2. 基于解析结果的技术栈和项目经历，针对性地出题
```

模型读到这段，用 `Bash` 工具执行，拿到输出继续往下走。框架要做的事情很少——只需让 Skill 目录的路径对模型可见（SOP 里用相对路径引用，框架保证工作目录或提示里带上这个路径）。

> 说明：这么做有个**必须知道的代价**。`allowedTools` 的安全价值建立在「Skill 只是一段 Markdown」这个前提上——后面会讲，一个恶意 Skill 想诱导 Agent 执行 `rm -rf /`，只要它的白名单里没有 `Bash`，模型就做不到。但**一旦 Skill 目录里带了脚本、而白名单里必须开 `Bash`**，这道墙就没了：加载第三方 Skill 就等于允许它执行代码。
>
> 这不是 ACode 独有的问题，走这条路线的实现都面对它。业界的常见应对是**在激活时刻做一次显式确认**——弹窗告诉用户「这个 Skill 将获得哪个目录的访问权」，用一次用户同意换取后续的自动化。ACode 这一步留待后续考虑，本章先把机制跑通。

### 资源引用要写在 SKILL.md 里

第三层资源不会自动进上下文，**所以 SOP 里必须写清楚有哪些资源、什么时候去看**。

```
## 参考资料

- 出题维度和技术栈映射见 `references/interview-guide.md`
- 需要生成面试报告时，套用 `assets/report-template.md`
```

不写的话模型不知道它们存在——这是实践中很容易犯的错：资源放进目录了，但正文里一个字没提，结果永远用不上。

**另外，正文里只写「指针」，不写「拷贝」。** 同一份信息不要既出现在 SKILL.md 里、又出现在 `references/` 里。SKILL.md 保持精简（核心流程和常用场景），详细内容放 `references/`。判断标准很简单：**每次激活都一定需要的信息留在正文，只在特定分支才需要的挪出去。**

### 可分发的能力包

目录型 Skill 还有一个常被低估的好处：**整套能力可以打包移植**。

整个 `backend-interview/` 目录是一个自包含单元——SOP、脚本、长文档参考全在里面。同事写好的 Skill 可以推到 Git 仓库或者打成 zip 分发，你 clone 或解压下来扔进 `~/.acode/skills/`，下次启动 ACode 就能直接 `/backend-interview`。

团队内部沉淀的最佳实践不再散落在各人的 prompt 收藏夹里，而是变成**可被代码评审、可被打版本号、可在 CI 里校验**的一份配置资产。

## `allowedTools`：把注意力收窄，也把危险挡住

回到 frontmatter 里那个「推荐填」的字段。你可能会觉得奇怪：工具不是越多越好吗？为什么要限制 Skill 能用哪些工具？

### 第一层理由：准确率

开头提过，工具太多模型会选错。当 commit Skill 的 `allowedTools` 只列了 `Bash`、`ReadFile`、`Grep` 三个，模型执行时的选择范围从二十几个骤降到 3 个，**选错的概率大幅降低**。

这就是渐进式披露在工具维度上的体现：每个 Skill 只暴露完成任务所需的子集，注意力集中在正确的选择上。

### 第二层理由：安全

这一层更重要。想象一个场景：

你从网上找到一个第三方 Skill，下载到 `~/.acode/skills/` 下面。你以为它是帮你格式化代码的，但实际上它的 SOP 里藏了一段恶意内容，试图诱导 Agent 执行 `rm -rf /`，或者把 `.env` 文件的内容发到外网。

如果这个 Skill 可以使用所有工具，这种攻击是完全可能成功的——**因为模型分不清「用户要求的」和「SOP 里写的」，对它来说都是指令**。

但如果它通过 `allowedTools` 限制了只能用 `ReadFile` 和 `Grep`，那么**无论 SOP 怎么写，Agent 都执行不了 `Bash`，也改不了文件**。

这就是**最小权限原则**在 Skill 系统里的体现。

### 语义：是「过滤」，不是「注册」

有一个必须讲清楚的区别：

- **`allowedTools` 管「可见性」** —— 这次执行能用哪些工具。它是**从已有工具里挑几个**
- **它不负责「注册」** —— 它不会创造一个原本不存在的工具

所以写法上有一个铁律：**不要把已有的内置工具之外的东西写进 `allowedTools` 来「声明」它**。`allowedTools` 里出现的名字，必须是主工具注册表里已经存在的工具；写了一个不存在的名字，是配置错误，不是新增工具。

> 说明：有的教材实现里还有一个 `tool.json`，用来在 Skill 目录中**声明一个专属的新工具**。ACode 本章**不做这个东西**，理由有两条：
>
> 第一，Claude Code 的官方 Skill 格式里**没有**这个机制——Skill 只负责「指令 + 资源 + 工具过滤」，要新增工具走的是另一条独立的路（插件 / MCP Server）。把「过滤」和「注册」分开，两件事各自都更简单。
>
> 第二，在 Java 里「让 Skill 目录里的文件变成一个可调用的工具」并不自然——ACode 的工具是编译好的类，没法在运行时从 Skill 目录加载一段实现代码进来。硬做要么绑死脚本语言、要么引入动态加载，收益不划算。
>
> 真需要专属工具时，**ACode 已有的做法是够用的**：把确定性逻辑写成 `scripts/` 里的脚本，让模型用 `Bash` 调（上一节讲的那条路）。它不是「工具」，但达成了同样的效果。

### 实现：两步，加一道校验

**第一步：空则不限。** `allowedTools` 没写（或为空）就不做限制，直接用全部工具。这是为了向后兼容，也方便在信任环境下快速写一个 Skill。

**第二步：非空则过滤。** 从主工具注册表里把点名的工具挑出来，组成一份工具列表交给 Agent Loop 用。

关于这一步有个值得注意的实现细节：**过滤不需要改动 `ToolRegistry`**。ACode 的 `Conversation.buildRequest(requestTools, turnReminder)` 里，工具列表本来就是**按请求传入**的——所以「过滤」只是传一份不同的列表进去，注册表本身不动。这让工具隔离变成一个很局部的改动。

**第三步（校验）：fail-fast 依赖检查。** Skill 执行的最开头，先扫一遍 `allowedTools`，确认每个名字都能在主注册表里找到对应的工具。**任何一个找不到就立刻报错返回**，不要等 Agent 跑起来再失败。

为什么要这么严格？设想一下：你写了个 Skill 声明用 `Bash`，但你换了个精简版配置，`Bash` 被关掉了。Skill 跑了两轮才发现工具不存在，这时候 token 已经烧掉一些了，错误信息还埋在一堆中间步骤里。这种「依赖丢失」的错误**越早暴露越好**。

### 和 SubAgent 的白名单字段正好相反

这里有个呼应值得提前记一下。后面 SubAgent 那一章（`docs/ch12/`）会有自己的工具白名单，但它**故意用了不同的字段和相反的默认值**：

| | 白名单语义 | 适合谁 |
|---|---|---|
| **Skill** | `allowedTools`：「你只能用这几个」 | 干一件具体的事，范围窄，**白名单更安全** |
| **Agent** | `tools` 白名单 + `disallowedTools` 黑名单：「排除这几个危险的，其余都能用」 | 扮演一个角色，**能力接近全集** |

为什么不统一？因为 Agent 扮演一个角色、能力接近全集——**逐个列出几十个允许的工具根本不现实**，反过来排除少数危险工具方便得多。

一个面向「干一件具体的事」，一个面向「扮演一个角色」。两套不同的东西，只是恰好都用了 Markdown + YAML 来定义。

## inline 还是 fork：要不要共享上下文

`mode` 字段的两个取值，是理解 Skill 系统另一个重要的概念。

### `inline`：共享当前对话

Skill 的正文加载进当前对话，和正常的用户消息一样走 Agent Loop。它可以看到之前的对话上下文，执行结果也会留在对话历史里。

```
[用户消息 1]
[Agent 回复 1]
[用户: /commit]            ← Skill 触发
[Skill 正文注入]            ← 进入当前对话
[Agent 执行 Skill]          ← 能看到消息 1 的上下文
[Skill 完成]
[用户消息 2]                ← 能看到 Skill 的执行结果
```

**为什么 `/commit` 适合 inline？** 因为 Agent 可能在前面的对话里已经帮你改了几处代码。Skill 需要知道这些改动的上下文，才能正确判断哪些文件该提交、message 该写什么。切断了这条信息流，它就做不出准确判断。

### `fork`：独立上下文

Skill 在一个独立的上下文里执行，不影响也不受当前对话影响——就像开了一个新的 Agent 会话，执行完后只把结果带回主对话。

```
[主对话]                    [fork 会话]
用户消息 1
Agent 回复 1
用户: /review
  ────────────→            Skill 正文（独立上下文）
  （主对话暂停）              Agent 执行审查
                             读文件、分析代码...
                             生成审查报告
  ←────────────            返回审查报告
Agent 显示审查报告
用户消息 2
```

**为什么代码审查适合 fork？** 因为审查应该是客观的。如果 Agent 之前在对话里说过「我觉得这个实现挺好的」，在 inline 模式下这句话会影响审查结果——**模型倾向于给自己的代码打高分**。fork 切掉历史，相当于换一个全新的视角进来，结果客观得多。

`context` 字段就是为 fork 服务的：客观审查用 `none` 最稳妥；需要看到背景摘要的场景用 `full`；想带一点背景但又不想被太多历史污染，用 `recent`。

### fork 的落地依赖 SubAgent

fork 要真的跑起来，需要「创建一个独立的 Agent 上下文、跑完拿回结果」这套能力。**这套能力不应该由 Skill 系统自己实现**——因为 SubAgent 那一章正好要建它。

教材里的方向是明确的：**SubAgent 的「Agent 构造 + 运行到完成」是共享底座，Skill 的 fork 通过委托的方式复用它**，两边走同一条创建路径。

所以本章把 inline 模式做完整，**fork 的委托接口搭好、`mode` / `context` 字段能解析能校验**，真正的子会话创建留到 SubAgent 章节展开。这和 `docs/ch11`（Hook）里 `agent` 执行器只搭骨架、`docs/ch12`（SubAgent）先建底座，是同一条推进逻辑。

> 说明：ACode 的 `Tool` 接口天然支持「Agent 即 Tool」，这为将来的委托留了余地——不过本章不展开。

## 激活之后：清理、重复加载、token 账

机制讲完了，还剩三个「用了之后才会遇到」的问题。

### 什么时候清理

SOP 进了对话历史，就会跟着对话走：

- **`/clear` 清空对话时，SOP 跟着被清掉**——这是「正文进历史」这个设计的附带好处，不需要额外写清理逻辑
- **上下文压缩时也一样**——压缩会重写历史，SOP 可能被摘要掉甚至删掉

被清掉之后怎么办？**不需要特殊保护，需要的时候重新加载就行。** 因为第一阶段的清单在 system prompt 里，压缩和清空都不碰它——模型随时能看到「有 commit 这个 Skill」，需要时再调一次 `LoadSkill` 把它拿回来。

> 说明：这就是「清单放 system prompt」这个决定的真正价值。**清单是索引，正文是缓存。** 索引持久、缓存可再生——不必费心去保护会被压缩的内容，只要保证索引一直在。

### 重复加载怎么办

模型有可能反复调用 `LoadSkill("commit")`。如果每次都往历史里追加一份完整正文，同一份 SOP 会出现两三份——重复花 token，还可能自相矛盾。

处理很简单：**维护一份「已激活」名单，已经在名单里的就不再重复追加**，直接回一句「已在上下文中」。

这份名单还需要和正文的生死保持一致：

```
LoadSkill("commit")  →  ① 追加正文进历史   ② 名单加上 commit
压缩 / /clear        →  ① 历史被重写        ② 名单清空
下次模型需要          →  重新 LoadSkill，两边一起回来
```

**两边同时生、同时死**，就不会出现「名单说已激活、历史里却没有正文」的错位。否则工具白名单还挂着（工具被收窄了），但 SOP 已经没了——模型既不知道该干什么，能用的工具还少了。

> 说明：压缩之后如果名单非空，值得顺手注入一句提醒（「commit 技能已失效，如需继续请重新加载」）。否则模型可能还在照着**摘要里的** SOP 干活，但白名单已经悄悄放宽了。一行字就能堵上这个缝。

### token 账

两个阶段的开销完全不同，搞清楚这件事才能理解为什么要这么设计：

| 阶段 | 在哪 | 开销 |
|---|---|---|
| 第一阶段（清单） | system prompt，落在 cache 稳定前缀区 | **恒定且便宜**。30 个 Skill 也只是几百 token 的 cache hit |
| 第二阶段（正文） | 追加进对话历史 | **按 Skill 数量和对话长度累计**。激活得越多、聊得越长，这部分越显著 |

所以有两条实用建议：**Skill 的正文要写得精炼**（够用就行，别把长文档塞进 SOP），**长内容放 `references/`**（那是第三层，只在需要时才读）。

## 两个内置 Skill

ACode 内置两个 Skill，覆盖最常用的场景。它们既是能直接用的生产力工具，也是写自定义 Skill 时的参考模板。

> 说明：`/review` 在本章的教材里是「从 ch09 的硬编码命令升级成 Skill」的案例。ACode 目前**不动它**——`/review` 继续沿用 ch09 的 `prompt` 类命令形态。内置 Skill 本章只做下面两个，理由是它们正好覆盖了两种最容易踩坑的场景（补全流程、区分归因），而且都不需要 `fork`，可以在 `fork` 落地前就跑通。

### `commit`：分析 diff 并生成规范的提交

流程很机械：先 `git status` 看全局，再 `git diff` 和 `git diff --staged` 看细节，区分 staged 和 unstaged 变更，按内容生成 conventional commit 格式的 message，逐个 `git add`，最后 `git commit`。变更覆盖超过 10 个文件时，主动建议用户拆分。

**为什么特意强调逐个 `add` 而不是 `git add -A`？** 因为 `-A` 容易把不该提交的文件一股脑带进来——`.env`、调试用的临时脚本。逐文件添加给了 Skill 一个机会去判断每份改动该不该上车，跟你手动 commit 时的习惯一样。这也是「Agent 只会照字面做」的一个正面例子：**你希望它怎么做，就得把「怎么做」写清楚**，光写「注意不要提交敏感文件」是不够的。

模式上是 `inline`：前面的对话里 Agent 可能刚帮你改了代码，这些改动是判断「该提交哪些文件、写什么 message」的关键依据。

### `test`：跑测试并区分两类失败

流程分三步：先根据项目配置检测项目类型（ACode 自己是 Maven 项目，跑 `mvn test`），再执行，最后分析输出。

**最关键的能力是区分两种失败：**

- 一种是**代码本身有 bug** 导致测试失败 → 要去改源码
- 另一种是**测试自己写错了** → 要去改测试

这两种修复方向完全不同，分错了就会一直往错的方向使劲。模型通过对比断言的期望值和实际行为、再翻一下相关代码上下文来做这个判断。这也是为什么 SOP 里要把这个判断过程**写具体**——只说「分析失败原因」，模型很可能随便归因。

如果所有测试都通过，它还会报告覆盖率并指出可能缺失的测试场景（边界值、错误路径）。**全绿不等于测试充分**，这一步是把「看起来没问题」和「真的没问题」区分开。

模式上也是 `inline`：你跑测试通常是为了验证刚刚讨论或修改的代码，前面的对话能帮 Skill 在分析失败时直接定位到相关位置，不必重新摸索整个项目。

## 设计哲学

**把 prompt 当资产，而不是当代码。**

一段精心设计的 prompt 有它自己的生命周期：会被修改、被评审、被分享、被打版本号。把它硬编码在 Handler 里，等于把它当成一次性代码——改一个字就要重新编译，只有开发者能动，别人只能复制粘贴。

搬到 Markdown 文件里之后，它就变成了**任何人都能编辑和分发的资产**。再配上三层查找（项目级覆盖用户级、用户级覆盖内置），团队的规范、个人的偏好、内置的默认，各自有各自的位置，谁也不挤谁。

第二个原则是**渐进式披露**：不是「把能力都塞给模型」，而是「先告诉它有什么，需要时再给细节」。这件事做了两层——Skill 层面（清单 → 正文 → 资源）和工具层面（`allowedTools` 收窄可见范围）。**上下文是稀缺资源，注意力更是。**

## 边界

- **不做 `tool.json`（专属工具注册）**。Skill 只负责「指令 + 资源 + 工具过滤」，要新增工具走 MCP 那条独立的路。需要专属能力时用 `scripts/` 里的脚本 + `Bash` 调用。
- **`fork` 只搭接口**。`mode: fork` 和 `context` 字段能解析、能校验，真正的独立上下文执行**委托给 SubAgent 运行时**，留到 `docs/ch12/` 展开。本章把 `inline` 做完整。
- **不动 ch09 的 `/review`**。它继续是 `prompt` 类命令。内置 Skill 本章只有 `commit` 和 `test`。
- **`references/` 的读取交给模型自己判断**。框架不做「什么时候该读哪个文件」的调度，而是靠 SKILL.md 里写清楚资源存在的指引。**写不清就等于没有。**
- **不做激活时的确认弹窗**。带脚本的第三方 Skill 存在「加载即信任代码」的风险，本章先把机制跑通，安全兜底留待后续。
- **不做跨平台同步**。Skill 是本地文件资产，不涉及云端分发。
- **不做嵌套调用的特殊处理**。Skill A 的 SOP 里再让模型加载 Skill B 是允许的（两条正文都进历史，同时在场），但不做深度限制、不做去重之外的额外防御——`inline` 路径天然被 Agent Loop 的最大轮数封顶。
