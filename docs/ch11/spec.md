# ACode 阶段十一：Hook 生命周期钩子与自动化 — spec

> 最后更新：2026-09-13
> 功能诉求见 `prompt.md`；本文只定"做什么/为什么"，不含函数名、参数名、默认值与错误文本；具体阈值与文案集中在 `checklist.md` 顶部
> 已确认的前置决策：**事件只做核心五个**（`pre_tool_use` / `post_tool_use` / `session_start` / `turn_start` / `turn_end`）；**Hook 的拒绝判定放在权限决策链得出"允许执行"的结论之后**（Hook 只能收紧、不能放宽）；**`agent` 执行器只留接口与调用骨架**，真实子 Agent 运行时留到下一章；**条件用 YAML 结构表达，不写表达式解析器**（`all` / `any` / `not` + `regex` / `glob`）；**`once` 的标记跟着会话走**——同一会话（含恢复该会话）内只触发一次，恢复会话不重新触发

## 背景

ACode 已经有四层安全防线（危险命令检测、路径沙箱、规则引擎、权限模式矩阵），它们在**工具调用**这个时刻做「放行 / 拒绝 / 询问」的判定。但它们都是**判定**，不是**动作**；也只覆盖**工具调用**这一个时刻。这留下三块空白：

- **重复动作无处声明**。Agent 写完一个源代码文件，用户手动跑一遍格式化；改完 `.proto`，手动跑代码生成器；新开一段对话，先手动贴一句"请先读 ARCHITECTURE.md"。这些动作的共同点是**触发条件明确、执行动作固定**——条件和动作都确定，每次一模一样，却每次都要人来触发。
- **非工具调用时刻无人可挂**。会话开始、一轮对话开始/结束，这些时刻权限系统结构上就够不着，用户想在这些时刻做点什么（注入背景、通知外部）没有任何入口。
- **判定的表达力受限**。一条权限规则是「工具名 + 单个内容字段 + 扁平 glob」——只能看一个字段、只有 `*` / `?` 两种通配、无法组合多个条件。而「工具是 Bash 且命令匹配某种写法」「写文件且路径不是 vendor 下的」这类策略，需要**跨字段组合 + 正则**才能表达。

本章给 ACode 加上 **Hook 系统**：让用户在生命周期事件上声明「什么时候 / 什么情况下 / 做什么」，事件发生时自动执行。这件事的定位是**补空白，不是替代**——既有四层防线一条不动，Hook 是在**权限链之后**再叠的一层用户可声明策略。

**要提醒的一点**：`prompt.md` 里「拦截 `rm -rf /`」那个例子，在 ACode 里**已经被既有危险命令检测硬拦截**了。这个例子在本章只作语法演示，**不是 Hook 的价值所在**——Hook 的价值是下面三类既有机制结构上给不了的东西：

| 既有机制给不了的 | Hook 提供的 |
|---|---|
| 只能判定，不能**做动作** | 跑命令、注入提示词、发 HTTP、起子 Agent |
| 只挂在**工具调用**上 | 覆盖会话开始、轮次开始/结束 |
| 单字段 + `*`/`?` 通配，**不能组合** | 跨字段组合 + 正则 |

## 目标用户

- **本人（日常使用者）**：把「写完代码跑格式化」「新会话注入项目背景」这类固定动作声明一次，之后自动发生；不用再当人肉 CI。
- **团队 / 多项目场景**：规则文件随仓库一起提交、一起 review，新同事 clone 下来就自动有了团队的安全策略与自动化规则。
- **下一章 SubAgent 系统（内部消费者）**：`agent` 执行器需要一个能启动子 Agent 的运行时——本章把接口与调用骨架就位，让下一章接上即用。

## 能力清单

### 一、配置与加载

1. **三处配置**：项目级、用户级、项目本地级各读一个配置文件，按顺序加载。
2. **追加合并**：三处的 Hook **叠加生效**，不是"找到一个就停"；本地级优先级最高，项目级与用户级声明的 Hook 同时可用。
3. **必填与可选**：事件与动作必填；条件可省，省即无条件执行。
4. **条目标识**：每条 Hook 有一个**跨重启稳定**的标识——显式声明，或由「配置文件 + 条目位置」稳定派生。校验报错、日志与 `once` 标记都靠它定位同一条 Hook。
5. **加载即校验**：配置在校验通过前不进入运行；不合法**当场拦下**并指出具体是哪一条、错在哪，而不是等真跑到那一步才炸。
6. **解析容错**：文件不存在、读取失败、格式坏掉都不导致启动失败；坏条目静默跳过，不影响其余 Hook 生效。

### 二、事件

7. **五个核心事件**：`session_start`（会话建立后）、`turn_start`（一轮对话开始）、`pre_tool_use`（工具执行前）、`post_tool_use`（工具执行后）、`turn_end`（一轮对话结束）。**未实现的事件名在校验期即被拒绝**，不会静默失效。
8. **唯一的可拒绝事件**：`pre_tool_use` 可以取消工具调用，其余四个事件只做通知，执行结果不影响主流程。

### 三、条件

9. **YAML 结构化条件**：条件是 YAML 结构而非字符串表达式，不需要为它写解析器；值里的空格、引号、反斜杠交给 YAML 本身处理。
10. **两个字段来源**：`tool`（工具名）与 `args.xxx`（工具参数中的某个字段）。**事件名不作为条件字段**——`event` 已经声明了这条 Hook 挂在哪个事件上，再写一遍是冗余。
11. **三种匹配方式**：精确相等、正则匹配、glob 匹配。
12. **组合方式**：多个字段默认是"且"；`all` / `any` / `not` 三个关键字可以任意嵌套，**层级即优先级**，不存在运算符优先级问题，也就不需要禁掉某种组合。
13. **未知字段不匹配且不报错**：条件里的字段取不到值时判为不匹配，而不是让整条 Hook 崩掉。
14. **glob 的路径语义**：glob 只用于路径类字段，`*` 不跨目录分隔符、`**` 跨任意层级、`?` 匹配单个字符。

### 四、动作执行器

15. **`command`**：起子进程执行 shell 命令，捕获输出与退出码；命令模板里的上下文变量在执行前展开；可设超时，超时则终止子进程并按执行失败处理。
16. **`prompt`**：不跑外部命令，把一段文本**注入到系统提醒区**（与既有的环境信息、提醒走同一条通道），**不进对话历史**——这样对话历史保持干净、token 计费可追踪。
17. **`http`**：向外部地址发一次请求，用于通知外部系统（Slack、日志收集、告警）。
18. **`agent`**：启动子 Agent 处理事件。**本章只留接口与调用骨架**——配置能通过校验、执行路径可达，但真实启动子 Agent 的运行时留给下一章；本章返回明确的未实现失败，不把空结果当作成功。

### 五、执行控制

19. **只执行一次**：可标记为触发一次后不再触发；标记**跟着会话走**——随会话持久化，同一会话内（含恢复该会话）只触发一次，**新建**的会话重新计。
20. **异步执行**：可标记为后台执行、不等待完成；**`pre_tool_use` 不允许异步**，配置校验拒绝这种组合。
21. **错误兜底**：Hook 执行出错只记日志、不中断 Agent 主流程；辅助机制的故障不影响核心任务。

### 六、上下文与变量替换

22. **上下文内容**：每次事件触发时收集该事件的上下文——事件名、工具名、工具参数、文件路径、消息内容、错误信息。
23. **变量替换**：动作的命令模板与请求体里可引用上下文变量，执行前展开；**未定义的变量替换成空字符串，不报错**。
24. **拒绝原因的传递**：`pre_tool_use` 的拒绝把动作产出的文本作为原因带回模型。

### 七、与主流程集成

25. **五处接线点**：五个事件各接在 Agent 主循环的对应时刻；Hook 引擎是 Agent 的一个可选依赖，未装配时行为与现在完全一致。
26. **判定顺序**：`pre_tool_use` 在**权限决策链得出"允许执行"之后**再问——无论这个"允许"来自自动放行还是用户确认。权限链判定拒绝的调用**不再问 Hook**。
27. **Hook 只能收紧**：Hook 的拒绝只可能把"允许"变成"拒绝"，**不存在任何让 Hook 放宽权限的路径**；既有四层防线的判定结果不被 Hook 改写。
28. **拦截即反馈**：被拒的工具调用不执行，**拒绝原因作为一次工具结果回给模型**，模型据此换一种做法完成任务——拦截不只是"堵"，还是一次纠正。
29. **多条匹配的顺序**：同一事件命中多条 Hook 时按配置里的先后顺序执行，**任一条拒绝即短路**，其后的不再执行。
30. **轮次的粒度**：`turn_start` / `turn_end` 对应用户的**一次输入到最终回复**，不是主循环的内部迭代——内部迭代（工具调用后继续请求）不重复触发这两个事件。

## 非功能要求

- **零新增依赖**：YAML 解析、正则、glob、子进程、HTTP 全部使用 JDK 与项目既有的 YAML 库；不引入规则引擎或表达式求值库。
- **逻辑层与终端解耦**：条件求值、变量替换、配置校验都不依赖终端，可在无终端的单测里直接断言（沿用既有纯逻辑组件的风格）。
- **不阻塞主流程**：同步 Hook 有超时上限，不会挂死主循环；标记为异步的 Hook 走既有的虚拟线程设施，不占用主循环线程。
- **辅助机制不反噬**：任何 Hook 的失败（命令非零退出、HTTP 失败、正则不匹配、配置坏条目）都只影响它自己那一次执行，**不改变工具调用是否执行、不改变会话状态**。唯一例外是被 `reject` 标记的拒绝——那是 Hook 的**正常产出**，不是失败。
- **自动动作不绕过权限**：`command` 与 `http` 在执行前经过现有权限边界；后台或无交互场景需要确认时跳过该动作并记录原因，不静默放行。动作失败不能转成一次有效的 `reject`。
- **配置错误可定位**：校验失败的提示必须能定位到具体条目与具体原因（事件名不合法、动作类型不合法、`reject` 用错事件、`async` 用错事件、必填字段缺失、条件结构不合法、正则无法编译）。
- **错误要分两处报，去处不同**：
  - **加载期的配置错误 → 打到终端**（沿用既有"配置出错在启动阶段直接打印"的约定）。项目既有的日志设施**只写文件、不进终端**（全屏界面会被 console 日志污染，这是有意配置），运行期日志在会话中是**看不见的**；而配置写错是用户必须当场知道的事，不能只落在看不见的文件里。
  - **运行期的执行错误 → 只写日志文件**。Hook 出错不打断主流程，也不在会话里刷屏。
- **会话文件向后兼容**：`once` 标记要落到会话文件里，而既有会话的每一行都是消息（角色 + 内容 + 时间戳），没有元信息行。新增的元信息行必须**不带消息字段**——既有的逐行解码把这类行当坏行跳过，因此既不破坏旧会话读取，也不影响旧版本读新文件；没有该元信息的老会话按"未触发过"处理，照常触发一次。
- **启动路径不退化**：没有配置文件时，启动与运行行为与本章之前完全一致。
- **视觉一致**：Hook 产生的输出（拒绝信息、提示词）沿用既有通道呈现，不新造渲染方式；不新增需要用户学习的新界面元素。

## 设计骨架

### 分层

```
┌───────────────────────────────────────────────────────────────────────┐
│  Agent 主循环                                                         │
│  session_start → turn_start → [请求模型] → 工具执行 → turn_end       │
├───────────────────────────────────────────────────────────────────────┤
│  Hook 引擎（Agent 的可选依赖）                                        │
│  事件分发 · 顺序执行与短路 · once 标记 · 异步派发 · 失败兜底          │
├──────────────────────────────┬────────────────────────────────────────┤
│  条件求值                    │  上下文                                │
│  YAML 结构 → 判定            │  字段取值 · 变量替换                   │
│  精确 / 正则 / glob          │  （事件名、工具名、参数、路径、消息…） │
│  all / any / not 可嵌套      │                                        │
├──────────────────────────────┴────────────────────────────────────────┤
│  动作执行器                                                           │
│  command（子进程 + 超时） · prompt（注入提醒区，不进历史）            │
│  http（外部请求） · agent（本章仅接口，下一章对接）                   │
├───────────────────────────────────────────────────────────────────────┤
│  配置加载                                                             │
│  三处 yaml · 追加合并 · 加载即校验 · 坏条目跳过                       │
└───────────────────────────────────────────────────────────────────────┘
```

### 一次工具调用的执行流

```
工具调用
  │
  ├─ 权限决策链（既有八步，一条不动）
  │     ├─ 拒绝 ──────────────────────────→ 直接拒绝，Hook 不参与
  │     └─ 允许（自动放行 或 用户确认）
  │           │
  │           └─→ Hook：pre_tool_use
  │                  ├─ 任一条 reject ──→ 取消本次调用
  │                  │                    拒绝原因作为工具结果回给模型
  │                  └─ 无 reject ─────→ 执行工具
  │                                        └─→ Hook：post_tool_use
  │
  └─（Hook 未装配时，这条链路与现在完全一致）
```

### 五个事件的接线点

```
session_start   会话建立后、首次请求之前
turn_start      一轮对话开始（向模型发请求之前）
pre_tool_use    权限链放行之后、工具执行之前        ← 唯一可拒绝
post_tool_use   每次工具调用返回之后
turn_end        一轮对话结束（模型给出最终回复、不再调用工具时）
```

### 条件求值的结构

```
条件（YAML）
  ├─ 字段映射     {"tool": 值, "args.path": 值…}   → 全部满足（隐式 all）
  ├─ all: [ … ]   → 全部满足
  ├─ any: [ … ]   → 任一满足
  └─ not: { … }   → 取反
          ↓ 递归求值
     每个字段匹配 → 精确 / regex / glob → 布尔
```

## 关键设计决策

| 决策点 | 结论 |
|---|---|
| 条件语法 | **用 YAML 结构，不写表达式解析器**（用户已确认）。书里的字符串语法（`tool == "Bash" && args.command =~ /.../`）要求自造解析器，随之带来四个纯粹是"自造语法"的代价：值里含空格要靠引号救、引号与正则斜杠要手工剥离、`=~` 与 `~=` 易记混、`&&` 与 `||` 因优先级问题只能禁止混用。改用 YAML 结构后这四条同时消失——空格引号反斜杠交给 YAML，组合靠 `all`/`any`/`not` 嵌套，层级即优先级。代价是与书的语法不同（书里本就承认各语言实现可不同）。 |
| 事件范围 | **只做五个核心事件**（用户已确认）。`pre_tool_use` / `post_tool_use` 覆盖绝大多数实际场景，`session_start` / `turn_start` / `turn_end` 是"不是工具调用"的那几个时刻；这三类合起来已能表达本次定下的全部实战场景。其余事件不为"看起来完整"而实现。 |
| Hook 与权限链的顺序 | **权限链得出"允许执行"之后再问 Hook**（用户已确认）。这样安全不变式极清晰：**Hook 只能收紧、不能放宽**，既有四层防线的结论不被改写；权限已判拒的调用也不必再问 Hook。代价是 Hook 观察不到被权限链拒绝的调用（审计类需求留待后续）。 |
| 拦截的分量 | **`reject` 只对 `pre_tool_use` 生效**。`post_tool_use` 时工具已执行完，再谈"拒绝"没有意义；这是逻辑必然，不是实现限制。对应地，`async` **不能**用在 `pre_tool_use` 上——它需要同步给出允许/拒绝的决定。两条约束都在**配置校验期**拦下。 |
| 条件的字段 | **不把 `event` 作为条件字段**。书里允许在条件里写 `event == "..."`，但 `event` 已由 Hook 的顶层字段声明，条件里再写一遍是冗余，且制造"两者不一致"的歧义空间。字段收敛为 `tool` 与 `args.xxx`。 |
| glob 与权限 glob 的关系 | **Hook 的 glob 与权限规则的 glob 是两套语义，各自独立**。权限规则是「工具名(模式)」的**扁平** glob（`*` 跨 `/`），把它改造成路径感知会**改变既有规则文件的含义**（如 `WriteFile(/etc/*)` 覆盖面缩水），属于破坏性变更；而 Hook 的 glob 只服务路径类字段，用户对 `*.java` 的直觉是"当前层"。两者写在不同的文件里、形状也完全不同（一个在 `工具名(模式)` 里，一个是 YAML 值），不会混淆。 |
| `prompt` 的注入通道 | **复用既有的系统提醒通道**，不新增 `role=system` 消息。项目里已有"包成用户消息、打提醒标签、只进请求不进历史"的现成机制，与书里描述的语义完全一致；复用它同时满足了"不污染对话历史结构"与"token 计费可追踪"。 |
| 轮次的粒度 | **`turn_start` / `turn_end` 对应用户的一次输入到最终回复**，不对应主循环的内部迭代。主循环内部"工具调用后继续请求模型"也是同一个 `turn` 变量，但那是实现细节；若照搬会在一次用户输入里触发多次，与用户理解的"一轮"不符。 |
| `once` 的语义 | **跟着会话走，恢复会话不重新触发**（用户已确认）。书里的做法是"只存内存、重启即重置"，但它没考虑 ACode 有会话持久化与恢复——恢复一个会话时用户预期是**接着上次继续**而不是开新会话；此时把标记抹掉，"新会话注入一次项目背景"就变成了"每次恢复都再注入一遍"。定为：标记随会话落盘、恢复时读回，同一会话内只触发一次，**新建**会话重新计。**连带要求**：`once` 依赖的标识必须跨重启稳定（见能力清单第 4 条），否则恢复后认不出是同一条 Hook。 |
| `agent` 执行器 | **留接口 + 调用骨架**（用户已确认）。本章做到"配置能过校验、执行路径可达、明确标注未实现"，下一章补上运行时即用；不做成"校验期就拒绝该类型"，否则下一章要同时改校验与实现两处。 |
| 失败的处理 | **Hook 执行出错只记日志、不中断主流程**。Hook 是辅助机制——格式化失败，模型写的代码还在；通知没发出去，任务成果不受影响。一个辅助机制的故障能反过来把核心流程搞崩是"尾巴摇狗"。**唯一的例外是 `reject` 标记的拒绝**，那是正常产出而非失败。 |
| 错误的可见性 | **加载期错误打到终端，运行期错误只落日志**。这条是查证既有日志配置后定的：项目的 Logback 明确"只写文件、不进终端"（`~/.acode/logs/acode.log`），因为全屏界面会被 console 日志污染——也就是说**运行期日志在会话中根本看不见**。若配置写错也只落日志，用户的 Hook 就会静默失效且无从察觉（尤其"条件写得不匹配"这类最典型的错误，表现就是"什么都没发生"）。故：校验错误沿用既有"启动阶段直接打印"的约定打到终端，用户启动即知；运行期执行错误只落日志，不在会话里刷屏。 |
| 配置校验的时机 | **加载时集中校验一次，不合法不进入运行**。校验项：事件名合法、动作类型四选一、`reject` 只在 `pre_tool_use`、`async` 不在 `pre_tool_use`、各动作类型的必填字段、条件结构形状与正则可编译。错误必须定位到具体条目与原因。 |
| 坏配置与坏条目的区别 | **整个文件读不动 → 跳过该文件；单条坏掉 → 跳过该条**。都是静默跳过、不影响其余 Hook 生效，因为配置错误不该让 ACode 起不来。这与"加载即校验"不矛盾：校验针对的是**结构合法但语义不合法**的条目（事件名拼错、`reject` 用错事件），这类要明确报错；而文件读不到属于环境问题，报错也帮不上忙。 |
| 不做 Hook 的查看命令 | **与权限规则同样只读、由用户直接编辑文件**。ch09 已确立"权限规则不做命令入口、规则文件由用户编辑"的立场；Hook 配置属同类——文件里看得到、改得动，再配一套命令是重复入口。连带地，`/hooks` 这类查看命令也不做（见 Out of Scope）。 |
| `rm -rf /` 的例子 | **只作语法演示，不作为 Hook 的价值论据**。ACode 的危险命令检测已硬拦截它（既有决策链第②步）。Hook 的价值是"动作""非工具时刻""可组合判定"这三件既有机制结构上给不了的事，不重复既有防线。 |
| 配置的形态 | **三处独立文件，追加合并**。与权限规则的"三层文件 + 跨层判定"不同：权限需要跨层求值（deny > ask > allow），Hook 是**叠加**语义——三处声明的 Hook 全部生效，不分层求值。本地级最高优先级只体现在**同类规则的执行顺序**上，不体现在覆盖上。 |
| 与既有测试的关系 | 既有权限链、工具执行、主循环的测试**不改语义**。Hook 未装配时链路与现在完全一致，因此既有测试应当原位通过；Hook 相关行为由新增测试覆盖。 |

## Out of Scope（本阶段明确不做）

- **SubAgent 运行时**（`agent` 执行器的真实实现）——本章只留接口与调用骨架，下一章对接
- **消息级事件**（`pre_send` / `post_receive`）——消息的预处理与后处理不在本章范围
- **系统级事件**（`startup` / `shutdown` / `error` / `compact`）——留待需要时再加
- **场景化事件**（`permission_request` / `file_change` / `command_execute`）——各需在权限层、工具层、命令层新埋点，是本章之外的工作量
- **Hook 的查看 / 启停 / 编辑命令**（`/hooks` 之类）——配置文件由用户直接编辑，与权限规则的立场一致
- **配置热重载**（改动配置文件后运行中自动生效）——启动时加载一次
- **`once` 的跨会话记忆**（记到会话之外，让**新建**的会话也不再触发）——`once` 只跟着单个会话走，新会话重新计
- **条件表达式的字符串语法**（书里的 `tool == "..." && ...`）——已改为 YAML 结构
- **Hook 放宽权限的任何路径**——Hook 只能收紧；"允许某操作"仍须走权限链或用户确认
- **条件的更多匹配能力**（数值比较、字段是否存在、集合成员、正则捕获回填）——本阶段只有精确 / 正则 / glob 三种
- **Hook 的作用域细分**（按目录、按工具、按轮次的条件启用）——只按事件与条件过滤
- **Hook 之间的依赖与编排**（一条 Hook 的输出喂给下一条、并行执行多条）——按声明顺序串行，命中拒绝即短路
- **Hook 执行的可视化与统计**（执行历史、耗时、成功率）——失败只记日志
- **条件里对工具结果的后置判断**（`post_tool_use` 按工具输出内容过滤）——后置事件只做通知，条件仍只看工具与参数
