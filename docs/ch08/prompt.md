# 记忆系统

> 跨会话存在

## 长期记忆

三类：

- 会话持久化，就是之前写的/resume显示的session

- 项目指令文件

- 自动记忆

## 项目指令文件

命名为`ACODE.md`，类似Claude Code的`CLAUDE.md`，在开始启动项目时就会先把这个读取了

内容大致为介绍项目背景、技术栈、代码规范、注意事项

优先级：

```
项目根目录/ACODE.md <-(项目级)最高优先级
项目根目录/.acode/ACODE.md  <-(项目级)可被.gitignore忽略
~/.acode/ACODE.md  <- 用户级(个人偏好)
```

上述三个文件依次加载(不存在就跳过)，但并不是覆盖，之间是内容拼接的形式(以`----`分割)，高优先级排在前边

项目级的`项目根目录/.acode/ACODE.md`主要是适配个人的开发，`项目根目录/ACODE.md`主要是团队协作的规范

同时使用@include 来解决ACODE.md文件内容臃肿的问题，格式为`@include 文件路径`；设定固定depth来防止文件间的循环引用导致的无限递归，使用一个集合去维护已遍历过的文件来防止文件重复加载；如果在项目级的文件中写的路径会逃逸当前项目要保证能拦截；

## 会话持久化

会话持久化使用`JSONL`，每行一个JSON对象，代表一个对象

追加写入、增量加载、中间读取错误格式内容直接跳过

### 存储格式

每条JSONL包含三个字段：`消息、内容、时间戳`，eg：`{"role":"user", "content":"内容","ts":1763951405}`

content内容可以是简单字符，也可以是block数组

ts是unix时间戳，是个整数

### 会话文件的组织

会话文件放到项目的`.acode/sessions`下，会话ID格式是`YYYYMMDD-HHMMSS-xxxx`，xxxx是十六进制随机字符串

读取的化直接文件扫描就好了

### 会话管理器

SessionManager管理`.acode`下的会话，Session对象是一个活跃的会话实例，持有打开文件的文件句柄。每次追加消息时同步写入JSONL文件，先写文件再更新内存

### 恢复会话

四个步骤：

一、逐行解析，失败跳过

二、验证消息链完整性，恢复时要追踪所有未完成的工具调用，截断到最后一个[所有工具调用都有结果]的位置，即把末尾无结果的丢弃

三、检查Token量，恢复对话会话很长，Token量过大的话，触发压缩阈值

四、插入时间跨度提示，如果距离上次活跃超过 24 小时，在对话中插入一条消息提醒 Agent：上次会话是什么时候，中间可能有代码变更，建议重新读取相关文件。这能有效避免 Agent 拿着过期的文件内容做决策。

### 过期会话处理

超过30天的没有活跃对话，自动清理，会话列表中活跃的排在前边

## 自动记忆

按内容性质分为四类：

用户偏好：放到`~/.acode/memeory/`，用户的个人编码习惯和风格要求，eg：`我喜欢简单的风格`

纠正反馈：放到`~/.acode/memeory/`，用户明确指出 Agent 的输出有问题并给出正确做法，eg：`用互斥锁而不是消息通道`

项目知识：当前项目的具体技术信息，放到`<项目根>/.acode/memory/`下，可以提交到Git与团队共享，也可以加到`.gitignore`

参考信息：本项目的外部链接和资料，放到`<项目根>/.acode/memory/`

目录结构：

```
.acode/memory/
	MEMORY.md    # 索引文件（注入到 message）
	user-prefers-any.md		# 每条记忆一个文件
	feedback-testing.md
	project-deadline.md
```

记忆文件格式：

```
---
name: user-perfers-any.md
description: 用户偏好使用 any 而非 interface{}
type: feedback
---

用户明确要求 any 替代 interface {}。
**Why**：
**How to apply**：
```

`MEMORY.md`索引文件只存指针，每行一条，格式简介：

```
- [偏好 any 语法](user-perfers-any.md) - 用户要求用 any 替代interface{}
- [项目 golang-migrate](project-deadline.md) - 数据库迁移工具选型
```

索引文件注入到 messages 时有上限：最多 200 行或25KB，超了会截断并附加警告。

提取与去重

每轮Agent Loop结束后，模型给出最终回复、不在调用工具的那个时刻。这时候在后台异步回顾本轮对话，看有没有什么值得记忆的东西。

提取的过程通过一次独立的LLM调用完成。系统把`MEMORY.md`索引和所有现有记忆文件的摘要清单发给模型，连同最近一轮对话，让它分析对话、按四个类别分别决定是否需要创建新记忆、更新已有记忆或删除过时记忆：

```
memoryExtractionPrompt = """
下面是当前的记忆目录清单和最近一轮对话。
分析对话，提取值得长期记忆的信息。

操作：
- 创建新记忆文件（写 frontmatter + 正文，更新 MEMORY.md 索引）
- 更新已有记忆文件（如果信息有变化）
- 删除过时记忆文件（同时从 MEMORY.md 移除指针）

分类：user / feedback / project / reference
已有相同含义的记忆不要重复创建。
没有值得记忆的内容就什么都不做。
"""
```

加载：跟ACODE.md走同一条管线

每次新会话启动时，MEMORY.md索引文件跟ACODE.md文件走同一条加载管线

项目指令和自动记忆索引作为上下文注入messages。如果某条记忆的详细内容跟当前任务相关，Agent可以用ReadFile去读对应的记忆文件。

**不做** ：向量数据库、RAG 检索。
