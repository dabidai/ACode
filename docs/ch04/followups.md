## 1. 渲染层改造：主屏可复制（原 ch00 / 阶段四）

### 触发问题

ACode 界面原用「备用屏幕 + 全屏重绘 + 自绘滚动条 + 鼠标捕获」渲染，换来滚动与界面完全受控，
却付出关键代价——**输出无法用鼠标划选复制**：备用屏幕屏蔽终端原生 scrollback 与选择、
鼠标捕获让点击选中彻底失效、每帧重绘打断进行中的选择。

### 核心改动

切换为「主屏幕 + 追加进原生 scrollback + 仅重绘底部活跃区」：

- 已完成内容（用户输入、回复、终态工具卡片）只打印一次进入原生回滚，可划选 / 复制 / 滚动
- 流式回复与工具卡片作为「活跃区」在屏幕底部原地更新，不触碰上方历史
- 删除备用屏幕、全屏重绘、自绘滚动条、视口数学、鼠标捕获等整套旧设施

### 关键设计决策

- **历史查看完全原生化**：滚动 / 选择全走终端，应用不维护视口
- **活跃区更新**：光标上移旧活跃区行数 → 清到屏尾 → 打印新内容；行数按显示宽度折行计算
- **超长回复**：仅重绘可见后缀；顶部已滚入回滚的内容不再改动（边界可能残留少量旧渲染，属架构固有）
- **光标锚点**：所有输出以换行收尾、停于行首；输入提交时擦除原输入行、由应用统一追加（避免双写）
- **会话选择菜单**：作为活跃区 overlay 渲染，不进入回滚
- **窗口缩放**：由终端原生回流；活跃区重绘检测到宽高变化先归零已写行数再重画（reflow 后旧行数失效）
- **输入层**：去掉鼠标捕获，仅保留键盘；流式回复随增量替换内容模型尾部、工具卡片在终态时提交一次

### 关键值 / 验收要点

- 活跃区重绘写序列：`\033[{up}A`（上移，up=min(已写行数, 屏高-1)，up>0 时写）→ `\033[J`（清到屏尾）→ 每段 `段内容\r\n`
- 全程禁止绝对定位转义（`\033[r;cH`）
- 折行按显示宽度（宽字符占 2 列），折点不切断宽字符与 ANSI 序列；SGR 颜色状态跨段延续
- 内容宽度恰等于终端宽度时行尾补 `\r`（化解 pending-wrap 幻影空行）
- 超长回复：上移行数钳制为 `min(已写行数, 屏高-1)`、新内容只取末尾可见段
- `appendCommitted` 写 `行\r\n`、进入回滚、不计已写行数
- 验收：Windows Terminal 直接划选历史输出复制、滚轮回看、超屏流式无错行、拖拽 resize 不重绘不错位、退出终端状态正常

### 明确不做

应用内分页回看、流式渲染节流、真彩色/图片/超链接富文本、多标签/分屏、异常终端（dumb）降级、复制格式定制

### 关联问题：流式输出乱码根因（原 ch00/bug.md）

流式回复中后段乱码、丢字（总是从长行/代码块/表格处开始变坏），而同一轮的历史/会话文件内容完整干净。

**根因**：不是渲染层问题，也不是 API 问题，而是 ACode 内部 `ArrayBlockingQueue(64)` 事件队列满载时
用 `offer()` **静默丢弃 delta**——`TurnCollector.onDelta` 先 `text.append(delta)`（历史永全）再
`events.offer(delta)`（队满返回 false 且无异常，该条 delta 只从显示端消失）。消费者每帧全量 markdown
重渲染 + 终端写屏，文档一长生产快于消费 → 队列填满 → 中后段 delta 成批丢弃。纯追加式写屏方案
（本节方案）修不了此 bug——delta 若已在队列丢失，写屏再干净也是缺内容。

**修复**：新增 `putSafe` 封装（阻塞 `put()` 满时背压追平 + `InterruptedException` 恢复中断位），
4 处 `offer()` → `putSafe()`（TurnCollector.java:38 StreamText、:47 ToolUseEvent、
Agent.java:407 emit、StreamingToolExecutor.java:112 ToolResultEvent）。

## 2. 工具权限确认（原 ch05 / 阶段五）

### 触发问题

工具层 `Permission`（READ/WRITE/EXEC）只标记、不拦截、不确认：`ToolExecutor` 对任何工具都不经
用户同意直接执行。Agent Loop 放大风险——模型一发起 WriteFile / EditFile / Bash，ACode 立刻落盘或
执行命令。

### 核心改动

- 非 READ 工具（WriteFile/EditFile/Bash）执行前弹确认；READ 工具自动放行，不打断既有并发调度
- 确认提示展示工具名 + 参数预览，用户据此判断是否放行
- 拒绝 → 返回「用户拒绝执行」失败结果给模型（is_error=true），模型可调整方案后重试，不中断整轮
- Ctrl+C / EOF 等价拒绝；非 y/n 输入重问，直到给出 y/n 或取消
- plan 模式只暴露 READ 工具与计划交付工具，天然不触发确认

### 关键设计决策

- **交互方式**：终端逐调用确认，不做批量/会话级放行（初始为 y/n 行输入，后由 ch07 改为 ↑↓ 菜单）
- **通信机制**：事件握手——agent 线程发 `ConfirmationRequestEvent` 阻塞等待，UI 主线程应答，
  无共享可变状态；`Confirmation.await` 50ms 轮询检查 cancelled（不可裸 take 永不醒）、
  `answer` 幂等、中断恢复中断位
- **注入性**：`ConfirmationGate` 为可注入函数接口，默认 `ALWAYS_ALLOW`；`StreamingToolExecutor`
  旧构造委托默认放行，存量测试零破坏；UI 提示处理器可注入桩
- **配置**：不引入 allowlist 配置，保持纯交互式

### 关键值 / 验收要点

- 拒绝文案「用户拒绝执行「<工具名>」」；参数预览截断 160 字符补「…」
- 确认提示「要执行 <工具> <参数预览> ？[y/n] 」；批准/拒绝状态行「（已批准执行 <工具>）」「（已拒绝执行 <工具>）」
- 事件 `ConfirmationRequestEvent(toolId, toolName, argsSummary, Confirmation)`
- 被拒绝的调用也有失败结果入历史，无悬空 tool_use；确认期间 Ctrl+C 等价拒绝、界面无残影

### 明确不做

配置文件 allowlist / 会话级始终允许、命令危险检测（安全分析/白名单/黑名单）、跨工具批量审批、
确认持久化记忆、授权自动超时/回收

## 3. 工具结果渲染（原 ch06 / 阶段六）

### 触发问题

`ToolCallDisplay` 把工具结果渲染成单行折叠卡——运行行「⏳ 调用工具 X(params)」+ 终态行
「▸ X(params) 成功/失败：<200 字符压缩预览>」。多行输出（Bash 日志、WriteFile 回显）被压成一行难读；
命令与输出不易分辨；无耗时信息。本项为 ch05/ui.md 四项 UI 需求的第一项。

### 核心改动

- 运行行「● Name(params)」替换「⏳ 调用工具 Name(params)」（工具名青色）
- 输出块：首行「  ⎿  <内容行>」按成败着色（成功绿 / 失败红），后续行「     <内容行>」对齐缩进、原色
- 去掉显式「成功/失败」文字，以首行颜色区分成败
- 耗时脚注「  ⎿  (<耗时>)」：<1s 显示毫秒（823ms）、≥1s 显示秒带一位小数（2.3s）
- 单条 >300 行截断，末尾补「…（输出过长，已截断）」；空结果出「（无返回结果）」占位

### 关键设计决策

- **耗时归属**：仅统计 `executor.execute` 实际执行时长（`System.nanoTime` 包裹），不含用户确认等待；
  确认拒绝 / 取消路径记 0
- **追加式兼容**：输出块逐行追加进回滚，每行只写一次、无光标重绘、可划选；运行行进回滚后不再改动
- **模型可见性**：运行行不进模型；终态输出块进模型（多行），供历史/续聊保留
- **事件模型**：`ToolResultEvent` 增 `elapsedMs` 字段（波及 5 处构造须一次性改齐），UI 无需另行配对

### 关键值 / 验收要点

- 运行行「● <工具名>(<参数摘要>)」；输出块首行「  ⎿  <内容行>」（成功绿/失败红）、后续行「     <内容行>」；脚注灰色
- `formatDuration`：`823→"823ms"`、`2300→"2.3s"`、`0→"0ms"`、`5000→"5.0s"`（`Locale.ROOT` 不产生逗号小数）
- 单条上限 300 行；`collapse()` 与 `MAX_RESULT_LENGTH` 已删除

### 明确不做

选择交互（→ch07）、代码 diff（→ch08）、多终端/多项目（→后续）、结果渲染语法高亮、
输出折叠/展开交互、命中高亮、自动滚动控制、耗时历史持久化

## 4. 选择交互：↑↓ 菜单 + AskUser（原 ch07 / 阶段七）

### 触发问题

ch05 的工具权限确认用 y/n 行输入，不直观、易输错、无方向键操作；且 AI 无法主动向用户发起选择——
模型只能「在回复里让用户输入」，无法把用户选择结构化回传给模型。本项为 ch05/ui.md 四项 UI 需求的第二项。

### 核心改动

- 确认执行改用 ↑↓ 选择菜单：`> 是` / `  否`，默认选中「是」；Enter 选中、Esc/Ctrl+C/EOF 取消（=拒绝）
- 新增 `AskUser` 工具：模型发起 question + N 个 options 的单选菜单，选中项作为工具成功结果回传模型
- 两处共用同一套菜单基础设施 `MenuKeySource` + `SelectionMenu`；/resume 会话菜单也改用之（选中箭头 `▸` 统一为 `>`）

### 关键设计决策

- **选中样式**：`>` 箭头 + 整行反显 `\033[7m`；未选中「两空格 + 文本」；菜单首行 header 原色
- **选择握手照搬 Confirmation**：`Choice` 通道 + `ChoiceRequestEvent` + await 轮询；
  `Choice.await` 50ms 轮询、cancel→null、中断恢复中断位；null = 取消
- **交互分发**：`StreamingToolExecutor` 识别 `InteractiveTool` 走 `executeInteractive`，耗时记 0（不含用户思考时间）
- **AskUserTool 权限 READ**：绕过确认门、自动进 plan 模式工具表；`inputSchema` 手写 string 数组
  （规避 BaseTool 把 ARRAY items 硬编码成 object）
- **包边界**：InteractiveTool/AskUserTool 放 agent 包，AskUserTool 在 ConversationController 构造器注册，
  tool 包零改动
- **无竞态**：每次调用独立 Choice 通道随事件携带，同轮多个交互调用由事件队列背压 + 主线程串行应答

### 关键值 / 验收要点

- 确认菜单选项固定「是/否」默认选「是」；Esc/Ctrl+C/EOF 等价取消
- 状态文案：确认「（已批准执行「X」）/（已拒绝执行「X」）/（已取消）」；选择「（已选择「X」）/（已取消）」
- AskUser：options 为空或非字符串数组 → failure「选项不能为空」、不弹菜单；取消 → failure「用户取消选择」
- 事件 `ChoiceRequestEvent(toolId, toolName, question, options, Choice)`；
  `inputSchema` required 含 question 与 options，options 为 `{"type":"array","items":{"type":"string"}}`
- /resume 菜单行为不变（`>` 箭头 + 反显、↑↓/回车/Esc 各试一遍）；菜单进出不污染回滚

### 明确不做

多选/复选菜单、模糊搜索、超屏翻页、鼠标选择、菜单超时自动取消、options 数量上限/图标/描述/默认值、
结构化回传（只回传选中项文本）、确认菜单始终允许/批量审批

## 5. 展示策略：只读摘要 + 写入 diff（原 ch08 / 阶段八）

### 触发问题

ch06 把工具执行结果一律渲染成输出块（`⎿` + 缩进内容 + 耗时脚注），其中 ReadFile 把整个文件内容
（上限 300 行）原样刷进回滚——读大文件时屏幕被挤占、回滚难翻。要求按工具性质分级展示。

### 核心改动

- 只读工具成功：一行摘要 + 耗时——ReadFile「返回 N 行（Lx-y）」带行号范围、Glob「返回 N 个匹配」、
  Grep「返回 N 条命中」；被截断时追加「（已截断）」；不再列出内容
- 写入工具：行级红绿 diff——`+` 新增绿、`-` 删除红；首行保留确认文案；新建文件全 `+` 行；
  EditFile 每段替换拆 `- 旧文` / `+ 新文` 对比行
- Bash 维持现状（需要看命令输出）；AskUser / ExitPlanMode 展示不变；失败一律照常显示错误正文

### 关键设计决策

- **展示分离**：`ToolResult.display()` 仅界面层消费，模型回传（`tool_result` content）与持久化不变；
  `withDisplay()` 返回带 display 的新副本，原对象不可变
- **diff 计算方**：写入工具在执行时计算（此时旧内容仍在磁盘）；渲染层只按行前缀通用着色
  （`"+ "`→绿、`"- "`→红），不按工具名硬编码，未来工具自动适用
- **LineDiff**：先裁共同前缀/后缀、仅对变更中段做 LCS（`int[o+1][n+1]` 矩阵，o+n ≤ 变更上限）——
  文件整体多大都不影响是否出 diff，只有「变更本身过大」才降级
- **旧内容读取**：>2MB 大小守卫不读、读取失败（非 UTF-8 等）不阻断写入；均降级提示
- **模型 payload 不变**：对话历史与持久化只存回传正文，`--resume` 历史渲染不受影响

### 关键值 / 验收要点

- ReadFile 摘要「返回 N 行（Lx-y）」（1 起行号；offset=0 即 L1-N）；Glob「返回 N 个匹配」；Grep「返回 N 条命中」
- LineDiff 变更中段（oldMid+newMid）总和 >300 行 → 返回 null → WriteFile display 末尾「…（变化过大，省略对比）」
- WriteFile 旧内容 >2MB → 「…（旧内容过大，省略对比）」；读取失败 → 「…（旧内容读取失败，省略对比）」
- EditFile 累计 diff 行 >300 → 「…（变化过大，省略对比）」；展示层 MAX_DISPLAY_LINES=300 截断沿用
- WriteFile/EditFile `output()`（回传模型）仍是原确认文案（「已写入 …（N 字符）」/「已编辑 …（N 处替换）」），不含 diff

### 明确不做

语法高亮、左侧行号、整行绿色/红色背景（ch05/ui.md 的完整 diff 需求，另立阶段）、行内（字符级）diff、
摘要行「点击展开」交互、diff 折叠/分页/一键回滚、Bash 输出展示变更、只读摘要文案个性化配置

## 6. 源需求：ch05/ui.md 四项 UI 需求与落地状态

## 7. 遗留清单

- 多终端 / 多项目并行（ch05/ui.md 需求 4，另立阶段）

- 输出折叠/展开交互、命中高亮、自动滚动控制

- 流式渲染节流（如手测出现卡顿再另行评估）
